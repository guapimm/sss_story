# 04 · 数据模型规格

> **用途**：定义新系统的完整数据模型（表结构 + 领域对象）。是 P0（建表）与 P1（领域层）的施工依据。
> **设计原则**：① 实体一等化 ② 强外键 ③ 单一章号 ④ 关系/归属/状态/事件四分离 ⑤ 大产物不入库
> **对照**：旧项目 27 表 / 358 列 / 0 外键 / 8 张空表 / 101 列可删（见 `research/01-data-and-storage.md`）。

---

## 1. 设计原则（每条都对应旧项目的实证缺陷）

| # | 原则 | 旧项目实证 |
|---|---|---|
| 1 | **实体一等化**：一切专名（人/势力/地点/物品/功法/规则）都有 `Entity` 行与 ID | 势力实体 **0 个**；地点是 40+ 碎片字符串；`participants` 大量为空 |
| 2 | **强外键**：除根表外每张表必须有 FK | 旧项目 **0 个 FK**，删书靠人工清单，**注释自承漏过 6 张表** |
| 3 | **单一章号**：全书单调递增 `int` | `vol*10000+idx` 双表示导致「已持续 10011 章」P0 事故 |
| 4 | **四分离**：关系 / 归属 / 状态 / 事件是四种东西 | 旧项目一张 `relationships` 表混装，导致 **86.7% 是非人际关系** |
| 5 | **大产物不入库**：正文/细纲 JSON 存文件，DB 存元数据 + hash | 旧项目 `books.outline` 单列存 400 章 JSON；`content_path` **80% 为空**且 3 种格式 |
| 6 | **枚举单一来源** | severity 代码 5 档 / prompt 3 档 → **最重的伤不催、轻伤催得最凶** |
| 7 | **无不可累积的边** | 旧项目归属用五元组匹配，写法一变即不停累积 |
| 8 | **遥测有 TTL** | 旧项目遥测 4 表占全库 **54%** 且无 TTL；`metrics` 与 `generation_attempts` 字段重叠重复记录 |

## 3. 核心表定义

### 3.1 `books`

```sql
CREATE TABLE books (
    id              INTEGER PRIMARY KEY,
    title           TEXT    NOT NULL,
    topic           TEXT    NOT NULL,           -- 创作主题/一句话设定
    mode            TEXT    NOT NULL,           -- 'story' | 'learn'（一期只 story）
    genre           TEXT    NOT NULL,           -- 题材（xianxia/suspense/...）
    scale           TEXT    NOT NULL,           -- fast/standard/grand/ultra
    target_chapters INTEGER NOT NULL,           -- 目标章数
    total_volumes   INTEGER NOT NULL,           -- ★ 规划出的卷数（非硬编码 3~6）
    -- 状态
    status          TEXT    NOT NULL,           -- created/planning/writing/paused/completed/failed
    current_volume  INTEGER NOT NULL DEFAULT 1,
    current_chapter INTEGER NOT NULL DEFAULT 0, -- ★ 单一章号
    -- 大产物引用（不入库）
    bible_ref       TEXT,                       -- 圣经文件 key
    bible_hash      TEXT,                       -- 内容 hash（供缓存/校验）
    -- 配置快照（便于复现）
    config_snapshot TEXT,                       -- JSON：本作品使用的配置
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL
);
```

**对照旧项目的改进**：
- `book.bible` 列被删除（旧项目该列在重开生成时被清空，且新书只写 `bible_path` → **每章 L0 圣经静默为空**）
- `total_volumes` 由规划决定，**不再硬编码 `scales.json` 的 3~6**（旧项目 ultra 档固定 3~6 卷 + 每卷 300~500 章 = 400 章挤一卷）
- 无 `status` 却用 `phase` 无约束 TEXT（旧项目 `Book.phase` 是无约束列、**43 处散落赋值、15 个状态**，且实测 `architecting` 不在 `ACTIVE_PHASES` → **重启后书永久卡死**）→ 新设计用 `BookStatus` 枚举 + 单一转换函数

### 3.2 `volumes`（对策②的落地）

```sql
CREATE TABLE volumes (
    id                  INTEGER PRIMARY KEY,
    book_id             INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    volume_no           INTEGER NOT NULL,
    title               TEXT    NOT NULL,
    -- ★ 升级台阶（必填，schema 强制）
    new_locations       TEXT    NOT NULL,   -- JSON list[entity_id] 或待创建的地点名
    new_factions        TEXT    NOT NULL,   -- JSON list
    antagonist_entity_id INTEGER REFERENCES entities(id),
    power_ceiling       TEXT    NOT NULL,
    core_conflict       TEXT    NOT NULL,
    escalation_from_prev TEXT   NOT NULL,   -- ★ 非模板句（有校验）
    -- 收尾
    old_map_closure     TEXT    NOT NULL,
    volume_end_hook     TEXT    NOT NULL,
    -- 规模
    chapter_start       INTEGER NOT NULL,   -- ★ 单一章号
    chapter_end         INTEGER NOT NULL,
    -- 台阶验收
    audit_status        TEXT,               -- pending/passed/failed
    audit_json          TEXT,
    UNIQUE(book_id, volume_no)
);
```

**旧项目对照**：卷信息塞在 `books.outline` JSON 里，后续卷 `blueprint="missing"`、`main_line=""`。
新设计把卷**升为一等表 + 必填字段**，模型无法通过省略来逃避扩张设计。

### 3.3 `entities`（对策①的落地）

```sql
CREATE TABLE entities (
    id              INTEGER PRIMARY KEY,
    book_id         INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    kind            TEXT    NOT NULL,           -- ★ 统一枚举，见下
    canonical_name  TEXT    NOT NULL,           -- 正名
    aliases         TEXT    NOT NULL DEFAULT '[]',  -- JSON list
    first_seen_chapter INTEGER NOT NULL,        -- ★ 单一章号
    last_seen_chapter  INTEGER,
    -- 生命周期（替代旧项目的名字前缀方案）
    lifecycle       TEXT    NOT NULL DEFAULT 'active',
                    -- active/destroyed_repairable/destroyed_permanent/lost_recoverable
                    -- /lost_permanent/consumed/declining/sealed/transferred/annihilated
    attributes      TEXT    NOT NULL DEFAULT '{}',  -- JSON，kind 专属，Pydantic 校验
    is_active       BOOLEAN NOT NULL DEFAULT 1,
    UNIQUE(book_id, kind, canonical_name)
);
CREATE INDEX idx_entities_book_kind ON entities(book_id, kind);
CREATE INDEX idx_entities_alias ON entities(book_id, canonical_name);
```

**`kind` 统一枚举（★ 关键修正）**：

```python
class EntityKind(str, Enum):
    CHARACTER = "人物"
    FACTION   = "势力"      # ★ 旧项目 entities.py 无此项，graph.py 也无 → 势力永远被降级为「其他」
    LOCATION  = "地点"
    ITEM      = "物品"
    TECHNIQUE = "功法"
    RULE      = "规则"
    TERM      = "术语"
    ORGANIZATION = "组织"    # ★ 与 FACTION 合并映射（旧项目「势力」vs「组织」并存导致匹配失败）
    OTHER     = "其他"
```

**旧项目三套词汇表冲突（必须修）**：
| 位置 | 词汇表 |
|---|---|
| `entities.py:17` | 有「组织」，**无「势力」** |
| `models.py:267` | 有「势力」 |
| `graph.py:36` | **两者都无** |

失效链：LLM 吐 `type="势力"` → `entities.py:146` 判非法 → 降级「其他」→ `graph.py:76-79` 再降一次。
实测后果：966 条关系中 `type_b='势力'` 仅 **7 条**。

**生命周期替代旧方案**：
| 旧项目 | 新设计 |
|---|---|
| `[毁·可修]青锋剑`（前缀塞在名字里） | `lifecycle='destroyed_repairable'` |
| 需专门写 `_strip_life_prefix`，且剥离**顺序敏感**（必须先在 `±` 之前剥，否则 `+[失·不可寻]家庭合影` 的残留会逃过归一化 —— `memory.py:668-669` 实证误杀） | 无字符串解析，无顺序依赖 |
| `[耗·一次性]` **既不在永久态也不在可恢复态**（`memory.py:216-220`），完全失管 | `consumed` 是明确枚举值，有对应处理 |

### 3.4 `locations`（层级化，解决碎片化）

```sql
CREATE TABLE locations (
    id                    INTEGER PRIMARY KEY,
    book_id               INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    entity_id             INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    parent_id             INTEGER REFERENCES locations(id),   -- ★ 自引用层级
    level                 TEXT    NOT NULL,   -- world/country/region/city/building/floor/room
    geography_tags        TEXT    NOT NULL DEFAULT '[]',
    controlling_faction_id INTEGER REFERENCES entities(id),   -- 可变（随剧情易主）
    is_accessible         BOOLEAN NOT NULL DEFAULT 1,
    UNIQUE(book_id, entity_id)
);
```

**实测问题**：旧项目书 23 的地点被拆成 40+ 个字符串变体
（`长明楼三层值班室` / `长明楼三楼档案科资料室` / `长明楼三层走廊` / `长明楼三层值班室门外`），
且 **77 次 location 为空**。

**层级化收益**：
- 可查询「三层有哪些房间」
- 可统计「第 N 卷新增几个 Location」（扩张闸门指标）
- 可算 `location_reuse_ratio`（防困在一处）

### 3.5 `entity_relations`（社会关系，含张力维度）

```sql
CREATE TABLE entity_relations (
    id                INTEGER PRIMARY KEY,
    book_id           INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    from_entity_id    INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    to_entity_id      INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    relation_kind     TEXT    NOT NULL,       -- ★ RelationKind 枚举（旧项目是自由文本 40+ 种）
    -- 张力维度（旧项目完全没有）
    intensity         INTEGER NOT NULL DEFAULT 50,   -- 0~100
    sentiment         TEXT    NOT NULL DEFAULT 'neutral',  -- positive/neutral/negative/conflicted
    surface_facing    TEXT,                   -- 世人所知（旧 visibility=明）
    true_facing       TEXT,                   -- 真实立场（旧 visibility=暗）
    is_mutual         BOOLEAN NOT NULL DEFAULT 1,  -- ★ 非对称关系
    -- 演化
    since_chapter     INTEGER NOT NULL,       -- ★ 单一章号
    status            TEXT    NOT NULL DEFAULT 'active',  -- active/changed/broken
    changed_by_event_id INTEGER REFERENCES events(id),
    updated_chapter   INTEGER NOT NULL,
    UNIQUE(book_id, from_entity_id, to_entity_id, relation_kind)
);
```

**旧项目的三处缺陷**：
1. **自由文本 `relation_type`**（实测 40+ 种，含 `归属/知情抽档` 斜杠复合）→ 改枚举
2. **五元组匹配把 `type_b` 当匹配键**（`memory.py:2763-2779`）→ 写法一变即匹配失败、旧边不解除、新边累积。实测 `顾长生→执法殿` 同时存在「归属」与「逃避/即将对峙」
3. **盲目把不同 `relation_type` 的旧边全置「解除」**（`memory.py:2802-2817`）→ 「归属」vs「所属」互相删除

**张力维度解决痛点 4（人物关系单一）**：旧项目人物-人物关系仅 **13.3%**，且全是静态标签
（`同门25 / 师徒24 / 盟友21`），没有强度、没有双向性、没有明暗张力。

### 3.6 `entity_affiliations`（归属，带时间区间）

```sql
CREATE TABLE entity_affiliations (
    id                INTEGER PRIMARY KEY,
    book_id           INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    entity_id         INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    faction_id        INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    role              TEXT,                   -- 职位/身份
    joined_chapter    INTEGER NOT NULL,
    left_chapter      INTEGER,                -- NULL = 仍在
    leave_reason      TEXT,                   -- 叛变/脱离/被逐/覆灭
    UNIQUE(book_id, entity_id, faction_id, joined_chapter)
);
```

**关键设计**：归属有**时间区间**，不是可累积的边。
旧项目归属走关系表（可累积）→ 换势力时旧边不解除、新边累积 → 「势力归属乱」。

### 3.7 `entity_states`（实体状态）

```sql
CREATE TABLE entity_states (
    id                INTEGER PRIMARY KEY,
    book_id           INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    entity_id         INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    field             TEXT    NOT NULL,       -- 位置/境界/目标/情绪/装备/性格/立场/口癖...
    value             TEXT    NOT NULL,       -- JSON
    tier              TEXT    NOT NULL,       -- immutable/event/mono_list/inventory/realm/injury/scalar
    updated_chapter   INTEGER NOT NULL,       -- ★ 单一章号
    UNIQUE(book_id, entity_id, field)
);
```

**替代旧项目的 `character_states.state` JSON 大对象**（旧项目 77 行、21 个字段混在一个 JSON 里，
其中伤势占 4 个键 —— 抽成独立表见 §3.8）。

**字段分级（`tier`）继承旧项目的正确设计**：
- `immutable`：外貌/出身/天赋（严禁改动）
- `event`：性格/立场/口癖/癖好/欲望（变更需事件支撑）
- `mono_list`：已学功法/机缘（只增不减）
- `inventory`：装备
- `realm`：境界（不可倒退/跳级）
- `injury` → **移到独立表**
- `scalar`：位置/目标/情绪

### 3.8 `injuries`（★ 对策④的落地：独立表 + 恢复计划）

```sql
CREATE TABLE injuries (
    id                    INTEGER PRIMARY KEY,
    book_id               INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    entity_id             INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    kind                  TEXT    NOT NULL,   -- 伤势/后遗症/心魔/代价/诅咒
    name                  TEXT    NOT NULL,
    severity              TEXT    NOT NULL,   -- ★ InjurySeverity 枚举（单一来源）
    status                TEXT    NOT NULL,   -- ★ InjuryStatus 枚举
    since_chapter         INTEGER NOT NULL,   -- ★ 单一章号（旧项目卷内号/全局号混用致 10011 事故）
    -- ★ 恢复计划（旧项目完全没有）
    expected_heal_chapter INTEGER,            -- 规划出的恢复章
    heal_scene_planned    BOOLEAN NOT NULL DEFAULT 0,  -- 是否已排入细纲
    heal_condition        TEXT,               -- 恢复条件
    -- 状态
    is_permanent          BOOLEAN NOT NULL DEFAULT 0,
    updated_chapter       INTEGER NOT NULL,
    resolved_chapter      INTEGER             -- 实际恢复章
);
```

**旧项目对照**：
- 伤势是 `CharacterState.state` JSON 里的 4 个键（不是表）
- 恢复的唯一闸门要求**三重巧合**（`memory.py:2114-2121`）：LLM 申报 + 同章 events 含治疗语义 + 事件文本**字面**含角色名 → **恢复率实测 0%**（36 条损伤无一走到「痊愈」）
- `architect.py` 中 `伤势|损伤` **0 命中** → 细纲层根本不规划伤
- `VALID_BEATS`（`schemas.py:25`）**没有 `heal`/`recovery`**

**新设计的三条硬约束**：
1. `expected_heal_chapter` 由 `HealthScheduler` 计算（阈值表 + 修正因子）
2. `heal_scene_planned=True` 才允许注入"需推进"提示（消除旧项目的死锁）
3. 报「痊愈」必须有结构化 `health_beats` 记录支撑（不再靠关键词匹配自由文本）

### 3.9 `events` + `event_participants`

```sql
CREATE TABLE events (
    id                INTEGER PRIMARY KEY,
    book_id           INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    chapter_no        INTEGER NOT NULL,       -- ★ 单一章号
    volume_no         INTEGER NOT NULL,
    story_time        TEXT,                   -- 故事内时间（文本，旧项目也是文本）
    location_id       INTEGER REFERENCES entities(id),  -- ★ 实体引用，非字符串
    description       TEXT    NOT NULL,
    consequence       TEXT,
    is_active         BOOLEAN NOT NULL DEFAULT 1,
    created_at        TIMESTAMP NOT NULL
);
CREATE INDEX idx_events_chapter ON events(book_id, chapter_no);

CREATE TABLE event_participants (
    event_id          INTEGER NOT NULL REFERENCES events(id) ON DELETE CASCADE,
    entity_id         INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    role              TEXT,                   -- 主体/客体/目击者
    PRIMARY KEY (event_id, entity_id)
);
```

**旧项目对照**：`story_events.participants` 是 JSON 数组存字符串名，
且实测**大量为空**（书 23 第 1 章所有事件的 `participants` 为 `[[]]`，尽管描述里明确写了"郑维向陈砚交班"）。
关联表 + FK 可强制完整性。

### 3.10 `llm_calls`（★ 对策⑦的落地）


**合并旧项目三张表**：`generation_attempts` + `generation_spans` + `metrics`
（旧项目 `metrics` 与 `generation_attempts` **字段重叠、同一次调用记两遍**；4 张遥测表占全库 **54%**）。

**必须有的 TTL**：旧项目遥测无 TTL → 无界增长。新设计保留 N 天（默认 90）后归档。

### 3.11 `foreshadowings`

```sql
CREATE TABLE foreshadowings (
    id                  INTEGER PRIMARY KEY,
    book_id             INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    fs_key              TEXT    NOT NULL,
    description         TEXT    NOT NULL,
    kind                TEXT    NOT NULL,     -- ★ 枚举（旧项目是文本）
    weight              TEXT    NOT NULL,     -- ★ 枚举
    plant_chapter       INTEGER NOT NULL,     -- ★ 单一章号
    planned_resolve_chapter INTEGER,          -- ★ 计划回收章（旧项目只有 resolve_ch，且卷末被无条件清空）
    resolved_chapter    INTEGER,
    -- ★ 防提前核销（旧项目卷末无条件 _force_recover_fs 把贯穿伏笔并入末章核销 → 第2卷末即清空）
    is_long_term        BOOLEAN NOT NULL DEFAULT 0,
    UNIQUE(book_id, fs_key)
);
```

**旧项目实测**：长篇伏笔回收率 **6%~23%**（书 8 仅 6%）。
根因之一是**卷末无条件 `_force_recover_fs`**（`pipeline.py:5994 → 5456`）把贯穿/长期伏笔
**并入末章核销**，且 ultra 要求 0 未回收 → **第 2 卷末就清空，后续无长线可收**。

新设计：`is_long_term` 标记贯穿型伏笔，**禁止卷末强制核销**。

## 4. 领域对象与表的关系

```
db 层（SQLAlchemy）          领域层（Pydantic，零框架零 SQL）
  Entity row          ←→     Entity / Character / Faction / Location / Item
  Injury row          ←→     Injury（含阈值计算、状态机）
  entity_relations    ←→     EntityRelation（含张力）
  volumes             ←→     VolumePlan（含扩张台阶）
  chapters.plan_json  ←→     ChapterPlan / SceneBeat / WorldStateSnapshot
```

**约定**：
- 领域对象**不依赖** SQLAlchemy
- 仓储层负责 row ↔ domain 转换
- 领域层的校验（Pydantic validator）是**唯一权威**；DB 约束是第二道防线

## 5. 大产物的存储（不入库）

| 产物 | 存储 | DB 里存什么 |
|---|---|---|
| 世界观圣经 | `data/books/{id}/bible.md` | `books.bible_ref` + `bible_hash` |
| 章节正文 | `data/books/{id}/chapters/{no:04d}.txt` | `chapters.content_ref` + `content_hash` + `content_len` |
| 章级细纲 | `data/books/{id}/plans/{no:04d}.json` | `chapters.plan_ref` + 关键字段（便于查询） |
| RAG 索引 | `data/books/{id}/index/`（分片） | 无 |
| 运行快照 | `data/books/{id}/runs/` | `runs.snapshot_ref` |

**旧项目的三个存储问题（必须避免）**：
1. **`content_path` 80% 为空**（1,147 / 1,441 章）且 **3 种格式混用**（`story/books/`、`learn/books/`、`books/`，**同一本书内也混用**）
2. `read_chapter` 读不到时**静默返回 `""`**（`docstore.py:212`）→ **正文丢失不报错**
3. `rag.json` 整份重写（book 8 达 **27.75 MB**）→ 286 章约 **2.9 GB 磁盘写**

**新设计要求**：
- 路径**由代码统一生成**（单一函数），不允许手工拼接
- 读取失败**必须抛错**，不返回空串
- 索引**增量更新**，不整份重写
- 每章产物有 `content_hash`，可用于校验与去重

## 7. 与 langgraph-checkpoint 的关系

| 内容 | 存放 | 理由 |
|---|---|---|
| 图执行状态（当前在哪个节点、重试计数、引用 ID） | **LangGraph checkpoint**（SQLite） | 框架原生能力 |
| 业务真相（正文、大纲、状态、账本） | **业务 DB + 文件** | 业务真相不能依赖框架 |
| 大产物 | **文件** | 防 checkpoint 膨胀（官方有 200 轮 5.3 GB 案例） |

**核心原则**（来自 `research/07` 的结论）：
> **把 LangGraph 当"可丢弃的加速器"而不是"真相来源"**。
> 业务真相放在自己的 DB；LangGraph 只负责编排、断点、人工介入与流式。
> 验收标准：`grep -r "langgraph" src/storyforge/domain/` 返回空。
