# 01 · 总体架构

> **定位**：定义新系统的分层、LangGraph 图结构、模块边界、目录布局。是 `04-分期实施计划` 的结构依据。
> **约束**：必须满足 `00-决策记录` 中的 D-01~D-12。
> **设计原则**：质量优先、可扩展性优先；单元化（每期一个可独立验收的功能）；大产物与图状态分离。

---

## 1. 分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  L5  接口层    CLI / HTTP API / 只读查看页                    │
│                （一期不做完整前端，D-05）                      │
├─────────────────────────────────────────────────────────────┤
│  L4  图编排层  LangGraph：主图（阶段）+ 子图（阶段内环节）      │
│                checkpoint / interrupt / resume                │
├─────────────────────────────────────────────────────────────┤
│  L3  节点层    Agent 节点（调 LLM）/ 确定性节点（零 LLM）      │
│                每个节点：单一职责 + 强类型输入输出             │
├─────────────────────────────────────────────────────────────┤
│  L2  领域层    实体模型 / 状态机 / 调度器 / 校验器 / 打分卡     │
│                纯逻辑，不依赖 LLM、不依赖 DB 细节              │
├─────────────────────────────────────────────────────────────┤
│  L1  基础设施  LLM 客户端（能力路由+计量）/ Prompt 库 / 仓储    │
├─────────────────────────────────────────────────────────────┤
│  L0  存储      SQLite（结构化）+ 文件（大产物）+ checkpoint DB  │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向**：L5 → L4 → L3 → L2 → L1 → L0，**严格单向**。
禁止：L2 调用 LLM；L3 直接写 SQL（须经 L1 仓储）；L4 含领域逻辑。

## 3. 编排架构：三级流水线 + 协调器（D-13）

### 3.1 为什么不是「一个大图」

用户要求的流程是**三级重叠流水线**：

```
圣经 ──[C-1 确认]──→ 骨架批次1 ──[C-2 确认]──→ 骨架批次2 ──→ 骨架批次3 ...
                        │                        │
                        └──→ 细纲批次1 ──────────┴──→ 细纲批次2 ──→ ...   ← 与骨架并行
                                  │
                          第1章细纲就绪
                                  │
                          [C-3 确认] ──→ 正文1 ──→ 正文2 ──→ ...          ← 与细纲并行
```

**若做成单图的两个分支，`interrupt()` 会冻结整个图** —— 确认第 1 章细纲时，
正在跑的骨架/细纲生产会被一起冻住，**用户要的并行就没了**。

**因此架构是**：

```
┌─────────────────────────────────────────────────────────────┐
│  协调器 Orchestrator（纯 Python asyncio，不含领域逻辑）        │
│  · 工作队列（按阶段）  · "谁领先"闸门  · 人工确认路由          │
│  · 启动/停止 worker  · 崩溃恢复                                │
└───────────────┬─────────────────────────────────────────────┘
                │ 每个「工作单元」调用一个独立的 LangGraph 图
    ┌───────────┼───────────────┬─────────────────────┐
    ▼           ▼               ▼                     ▼
 骨架批次图   细纲批次图      单章图              台阶图/圣经图
 (thread_id=  (thread_id=    (thread_id=         (thread_id=
  skel-v1-b3)  det-v1-b2)     ch-00042)           vol-plan)
    │           │               │
    └───────────┴───────────────┴──→ 共享 DB（唯一真相）
```

**收益**：
| 项 | 说明 |
|---|---|
| 并行天然成立 | 三个 worker 独立推进，互不阻塞 |
| 人工确认 = worker 等待 | 不是"全图暂停"，其他 worker 照常跑 |
| **崩溃恢复更精确** | 单元级：只重跑未完成的那一批，不重跑整个阶段 |
| 状态更小 | 每单元一个 `thread_id`，checkpoint 天然分片（防膨胀） |
| 与调研一致 | 「用确定性 custom workflow，不要 supervisor 自由路由」 |

### 3.2 协调器职责（严格边界）

**协调器只做编排，不含领域逻辑**：

```python
class Orchestrator:
    """纯编排：队列 + 闸门 + 唤醒。领域逻辑全在 domain/ 与图中。"""
    
    async def run(self, book_id: int) -> None:
        # 三阶段 worker 并发启动
        await asyncio.gather(
            self._skeleton_worker(book_id),   # 骨架：批次串行
            self._detail_worker(book_id),     # 细纲：批次串行，跟骨架
            self._chapter_worker(book_id),    # 正文：严格串行，跟细纲
        )
    
    async def _detail_worker(self, book_id: int):
        while not self._done(book_id):
            batch = await self._next_detail_batch(book_id)   # 依赖：骨架该批已就绪
            if batch is None:
                await self._wait_for("skeleton", book_id)    # 闸门：等上游，不空转
                continue
            await run_graph("detail_batch", batch)           # 调用细纲批次图
```

**关键机制**：
| 机制 | 设计 |
|---|---|
| **闸门（Gate）** | 细纲批次 N 需要骨架批次 N 已完成；正文第 M 章需要细纲第 M 章已就绪。用 DB 状态判定，不用内存标志 |
| **等待不空转** | 用 `asyncio.Event` 或 DB 轮询（间隔 ≥2s）**且必须留痕**（旧项目预生成线程曾 6 秒轮询空转，无日志） |
| **并发上限** | 骨架 worker=1、细纲 worker=1、正文 worker=1。**阶段内严格串行**（防旧项目的并行起草上下文错乱） |
| **人工确认** | worker 到达确认点时把状态写 `pending_confirm` 并**释放**，不阻塞其他 worker |
| **崩溃恢复** | 启动时扫描未完成工作单元 → 重建队列（不重跑已完成单元） |

### 3.3 「谁领先」的推进规则

```
骨架批次 N 完成
  ├─ 触发 C-2 人工确认（仅 N==1）
  ├─ 入队 细纲批次 N
  └─ 入队 骨架批次 N+1

细纲批次 N 完成
  ├─ 若 N==1 且第1章细纲就绪 → 触发 C-3 人工确认
  └─ 入队 正文（逐章，需细纲就绪）

正文第 K 章完成
  ├─ K==3 → 触发 C-5 黄金三章确认
  └─ 入队 正文第 K+1 章（需细纲 K+1 就绪）
```

**领先度限制**（防质量失控）：正文**最多领先细纲 N 章**（默认 3，即细纲至少要多备 3 章）。
理由：旧项目 `kick_min_ready=3` 的设计意图正确 —— 让正文有细纲缓冲，
但又不能无限领先（否则细纲无法根据正文实际产出校正）。

### 3.4 与 LangGraph 的分工

| 层 | 负责 | 不负责 |
|---|---|---|
| **协调器** | 队列、闸门、并发控制、人工确认路由、崩溃恢复 | 任何领域逻辑、任何 LLM 调用 |
| **LangGraph 图** | 单个工作单元内部的步骤编排、重试、单元内断点 | 跨单元的调度 |
| **domain/** | 领域逻辑（校验、调度器、状态机） | 编排、IO |
| **业务 DB** | 唯一真相 | — |

**验收**：`grep -r "langgraph" src/storyforge/domain/` 返回空；`grep -r "asyncio" src/storyforge/domain/` 返回空。

### 3.5 图的拆分（工作单元）

| 图 | 触发 | 内部步骤 | `thread_id` 示例 |
|---|---|---|---|
| `bible_graph` | 开书 | 圣经生成 → 校验 → **[C-1]** | `bible-{book_id}` |
| `volume_plan_graph` | 圣经后 | 全卷升级台阶 → `structure_gate` → 补缺 → **[C-4]** | `volplan-{book_id}` |
| `skeleton_batch_graph` | 台阶后 / 上批完成 | 本批骨架生成 → 校验 | `skel-{book_id}-v{vol}-b{batch}` |
| `detail_batch_graph` | 骨架该批就绪 | 本批细纲生成 → `outline_lint` → 伤势节拍注入 | `det-{book_id}-v{vol}-b{batch}` |
| `chapter_graph` | 细纲该章就绪 | 见 §3.6 | `ch-{book_id}-{global_no}` |

**每个图都是独立的 `StateGraph`**，有独立的 State 定义与 checkpoint 命名空间。
**它们不互相调用**（只由协调器调用），因此不存在子图嵌套的复杂度。

### 3.6 `chapter_graph`（单章闭环）

```python
builder = StateGraph(ChapterState)

# ── 写前准备（零 LLM）──
builder.add_node("assemble_context",   assemble_context_node)   # 三层 prompt 组装
builder.add_node("readiness_gate",     readiness_gate_node)     # 细纲就绪闸门

# ── 生成 ──
builder.add_node("write",              write_node)              # ChapterWriter

# ── 确定性校验（零 LLM）──
builder.add_node("score",              score_node)              # 打分卡
builder.add_node("continuity",         continuity_node)         # 状态连续性
builder.add_node("route_review",       route_review_node)       # 触发判定

# ── 按需审校 ──
builder.add_node("review",             review_node)             # StyleCritic（LLM）
builder.add_node("revise",             revise_node)             # TargetedReviser（LLM）
builder.add_node("recheck",            recheck_node)            # 重打分

# ── 提交（原子）──
builder.add_node("extract",            extract_subgraph)       # 事件/状态抽取
builder.add_node("resolve_entities",   resolve_entity_node)     # 实体归一
builder.add_node("extract_relations",  extract_relation_node)   # 关系抽取
builder.add_node("commit",             commit_node)             # 单事务提交

builder.add_edge(START, "assemble_context")
builder.add_edge("assemble_context", "readiness_gate")
builder.add_conditional_edges("readiness_gate", gate_router,
    {"ready": "write", "not_ready": END})       # 不就绪 → 干净退出
builder.add_edge("write", "score")
builder.add_edge("score", "continuity")
builder.add_edge("continuity", "route_review")
builder.add_conditional_edges("route_review", review_router,
    {"review": "review", "commit": "extract"})
builder.add_edge("review", "revise")
builder.add_edge("revise", "recheck")
builder.add_conditional_edges("recheck", recheck_router,
    {"pass": "extract", "retry": "revise", "give_up": "commit"})   # 有重试上限 → C-7
builder.add_edge("extract", "resolve_entities")
builder.add_edge("resolve_entities", "extract_relations")
builder.add_edge("extract_relations", "commit")
builder.add_edge("commit", END)
```

**设计要点**：
1. **确定性优先**：`score`/`continuity`/`readiness_gate` 零 LLM，先跑；只有触发才调 LLM
2. **失败隔离**：抽取是**三个独立节点**（旧项目是一个 10,000 字符 prompt 抽 11 类）
3. **原子提交**：`commit` 单事务完成「写 DB + 写文件 + 更新账本」
4. **不就绪干净退出**：不空转
5. **重试上限 → 触发 C-7**：不无限烧 token

## 4. State 设计（防 checkpoint 膨胀）

**核心原则**：State 只放**轻量状态与引用**，大产物（正文、细纲 JSON）存外部，State 持 ID。

```python
class ChapterState(TypedDict):
    book_id: int
    global_no: int                 # ★ 单一章号（D-15）
    plan_ref: str                  # ChapterPlan 存储 key
    content_ref: str | None        # 正文存储 key（不是正文本身）
    scorecard: dict | None
    violations: list[dict]
    review_result: dict | None
    retry_count: int
    status: str
```

**旧项目教训**：`pipeline.py` 把 outline/bible/characters/content 全塞进 `Book` 的 JSON 列，
导致 `books.outline` 单列存 400 章大纲。**LangGraph 官方承认 checkpoint 200 轮可达 5.3 GB** —— 必须引用化。

**LangGraph 三条硬约束（调研实测，写入反模式检查）**：
1. **节点不得原地修改 state**（`#8314` 引用透传会污染调用方输入）
2. **并行分支不得写同一状态键**（`#8115` 静默丢 checkpoint，30/30 复现）
3. **时间存 UTC ISO8601 字符串**（`#8826` datetime 静默丢时区）
4. **LLM 节点必须幂等**（`#7417` >180s 调用被静默重放 → 2~3× 成本）

## 4. 模式能力层（D-08：预留 learn 接口）

### 4.1 为什么不用继承树

旧项目 `flowmode/` 的思路（把模式差异外置）是**正确的**，但形态有三个问题（实测）：

| 问题 | 实测证据 |
|---|---|
| **上帝接口** | `FlowMode` 基类 **37 个方法**，`_flow(book).` 调用点 **48 处**（pipeline 46 + bible_rebuild 3） |
| **方向反了** | 现在是 **story 侧给 learn 钩子写空实现**（`story_flow.py:171-201` 有 8 个 `@staticmethod` 空实现）。应该是 learn 侧为 story 未用到的能力占位 |
| **门面外仍有直读** | 门面之外仍有 **30+ 处**直接判 `book_kind`：`main.py:1304` 直取 `_is_story`（路由层绕过门面）、`main.py` 7 处 `kind=="story"`、`drift.py` 4 处 `is_story` 形参、`architect.py:2895/2916` 裸 `_flow.kind`、`continue_story.py` 6 处 `book.book_kind` |

### 4.2 新设计：8 个 Protocol 组合 + 显式占位

```python
# modes/protocols.py —— 每个 Protocol 职责单一，可独立实现/替换
class LearningMapProvider(Protocol):
    def build_map(self, topic: str) -> LearningMap: ...

class TeachingLedgerProvider(Protocol):
    def record_taught(self, chapter_no: int, points: list[Point]) -> None: ...
    def untaught(self) -> list[Point]: ...

class KnowledgeCardProvider(Protocol):
    def extract_cards(self, prose: str, points: list[Point]) -> list[Card]: ...

class ResearchProvider(Protocol):
    def research(self, topic: str) -> ResearchResult: ...     # 旧项目用 Tavily

class FactVerifier(Protocol):
    def verify(self, claims: list[Claim]) -> list[VerificationResult]: ...

class Estimator(Protocol):
    def estimate(self, scope: Scope, scale: Scale) -> Estimate: ...

class GenrePlugin(Protocol):
    def writer_blocks(self, ctx: Context) -> list[str]: ...
    def extract_hints(self) -> str: ...

class PromptPack(Protocol):
    def writer_system_extension(self) -> str: ...
    def extractor_instructions(self) -> str: ...
    def critic_instructions(self) -> str: ...
```

**模式 = 这些 Protocol 的组合**：

```python
# modes/story.py —— 一期唯一实现
class StoryMode:
    """story 只需 PromptPack + GenrePlugin + Estimator；
    learn 专属的 5 个 Provider 不实现。"""
    def __init__(self, ...):
        self.prompts: PromptPack = StoryPromptPack()
        self.genre: GenrePlugin = GenrePluginImpl()
        self.estimator: Estimator = StoryEstimator()

# modes/learn.py —— 一期显式占位
class LearnMode:
    """一期不做。调用即抛错，不静默返回错误结果。"""
    @property
    def learning_map(self) -> LearningMapProvider:
        raise NotImplementedError(
            "learn 模式尚未实现（决策 D-08：一期只做 story）。"
            "若需启用，请实现 LearningMapProvider 等 5 个 Protocol。"
        )
```

| 旧项目 | 新设计 |
|---|---|

### 4.3 AST 检查器（把规约变成机器约束）

```python
# tests/contract/test_no_mode_branching.py
def test_shared_code_has_no_mode_branching():
    """共享代码（domain/ + graph/nodes/）不得直接判模式。
    所有模式差异必须经 modes/ 层的 Protocol。"""
    forbidden = {"book_kind", "is_story", "_is_story", "kind == \"story\""}
    for path in walk("src/storyforge/domain", "src/storyforge/graph/nodes"):
        tree = ast.parse(path.read_text())
        for node in ast.walk(tree):
            if isinstance(node, ast.Compare) and contains_forbidden(node, forbidden):
                pytest.fail(f"{path}:{node.lineno} 出现模式分支，应经 modes/ Protocol")
```

这条测试直接防止旧项目「门面建成但门面外仍有 30+ 处直读」的问题复发。

## 5. 关键机制设计

### 5.1 三层 Prompt 组装（对策⑦，缓存命中核心）

```python
# infra/llm/prompt_builder.py

class PromptLayers(BaseModel):
    stable: str        # 全书不变：角色定义 + 输出约束 + 圣经
    semi_stable: str   # 按卷/段变化：卷台阶 + 段目标 + 文风规则（固定文本）
    volatile: str      # 每章变化：状态表 + 时间线 + 前文 + 本章细纲 + 字数参数

def assemble(layers: PromptLayers, capability: ModelCapability) -> list[Message]:
    """按模型缓存能力组装。
    AUTOMATIC_PREFIX → stable 放最前，逐字节稳定
    EXPLICIT_CONTROL  → 在 stable 末尾插 cache_control 标记
    NONE              → 仍按 stable→volatile 顺序（便于分析）
    """
```

**CI 检查**：同书相邻两章的 `stable` 层 hash 必须相同。这条检查直接防止旧项目「`.format(MIN_CHARS=...)` 让 system 逐章变化」的问题复发。

### 5.2 实体归一（对策①）

独立节点 `entity_resolver`，不在抽取 prompt 里做：
```
输入：本章新提及的名字（来自 SceneExtractor.entities）
      + 既有实体表（canonical_name + aliases）
输出：对既有实体的链接 OR 新建实体
策略：① 精确正名匹配  ② 别名匹配  ③ 规范化匹配（去空格/繁简/尊称）
      ④ 地点层级推断（"长明楼三层值班室" → parent=长明楼/三层）
      ⑤ 相似度兜底（仅在 ①②③ 未命中时，且需 LLM 确认）
```
**关键**：地点必须有**层级推断**规则，否则碎片化会复现。

### 5.3 伤势节拍调度（对策④）

`HealthScheduler` 是**零 LLM 的确定性调度器**：
```
每当细纲规划到第 N 章：
  1. 取所有 expected_heal_chapter ∈ [N, N+window] 的活跃伤势
  2. 为每条生成 HealthBeat（按 4.3 的预热序列）
  3. 把 HealthBeat 注入 ChapterPlan.health_beats
  4. 校验：每个 HealthBeat.scene_ref 必须指向真实 SceneBeat
```
这解决了「恢复必须在大纲细节里补充好，不然太突然」这个用户痛点——**恢复节拍由调度器自动排入细纲，而非依赖规划模型记得写**。

### 5.4 卷级台阶闸门（对策②）

`structure_gate` 是**阻断式**校验器（不再是旧项目的 `shadow: true`）：
```
校验项（全部 required）：
  volume.new_locations ≥ 2 且 不与既往地图重复
  volume.new_factions ≥ 2
  volume.antagonist 与既往卷互异
  volume.escalation_from_prev 非模板句（正则 + 长度 + 与上卷差异度）
  volume.chapter_budget ∈ [150, 250]
  volume.milestones 数量 ≥ chapter_budget / 25
  全局：milestone 最大间隔 ≤ 25 章
  全局：总分配合 target_chapters（Σ chapter_budget == target）
失败 → 阻断，进入增量补缺子图（不用全量重写，旧项目实测大输出必被截断）
```
