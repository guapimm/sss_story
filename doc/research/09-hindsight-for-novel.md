# 09 · Hindsight 能否用于小说检索 / 逻辑链路？（三轮反复分析）

> 记录日期：2026-09-17
> 触发：负责人提问「能否用 Hindsight 优化小说检索或逻辑链路提升写作质量？
> 旧项目已用 bge-m3 + BM25，Hindsight 能带来什么提升」
> 方法：读 Hindsight 0.9.2 源码（`F:\conda-env\...\site-packages\hindsight_api`）
> + 读旧项目检索实现（`story_llm/backend/app/hybrid.py` 等）+ 实机探查

---

## 0. 结论先行（三轮分析后的定论）

| # | 结论 | 置信度 |
|---|---|---|
| 1 | **Hindsight 的检索能力确实强于旧项目**（4 路召回 + 图扩展 + 时序 vs 旧项目 2 路） | 高（源码可比） |
| 2 | **但它不是为"单本书内部检索"设计的** —— 它是**跨会话的 agent 记忆库**，粒度是"事实/记忆单元"，不是"章节正文片段" | 高 |
| 3 | **拿它替代小说内检索 = 用错工具**，且会引入三个硬问题（见 §3） | 高 |
| 4 | **它有真实价值的用法是另一个**：把**写作规范/教训/风格约束**变成一个可检索的 bank，供 writer 节点拉取 —— 即"**写作知识库**"，不是"小说记忆库" | 中高 |
| 5 | **绝不要**把小说正文灌进 Hindsight 来当 RAG（成本、语义错配、与既有 SQLite 账本重复） | 高 |

**一句话**：Hindsight 解决的是"**这个项目该怎么写小说**"（跨会话经验），
不是"**这本书里前面发生过什么**"（书内记忆）。前者是它的强项，后者该用既有账本 + 自建检索。

## 1. 两者的定位差异（这是全部结论的根源）

| 维度 | Hindsight 0.9.2 | 旧项目 RAG（`hybrid.py`） |
|---|---|---|
| **设计目标** | agent 的**长期记忆**：跨会话记住"用户是谁、项目怎么决策的" | 单本书**正文检索**：写第 N 章时找回前文相关段落 |
| **存储单元** | memory/fact（经 LLM 抽取+归并的事实） | 章节切片（原始文本 chunk） |
| **写入代价** | **每批都要调 LLM**（`fact_extraction` + `consolidation`） | 一次 embed（本地 bge-m3，零 LLM） |
| **bank 粒度** | `{bank_id}` 隔离，一个 bank = 一个记忆域 | 一本书一个目录 |
| **召回** | 4 路（semantic + bm25 + graph + temporal）RRF 融合 | 2 路（向量 + bigram-BM25）RRF |
| **时间维度** | ✅ `temporal_extraction.py` + `retrieve_temporal_combined_sql` | ❌ 无（靠 `story_time` 字段人工维护） |
| **图扩展** | ✅ `link_expansion_retrieval.py`（367 行）| ❌ 无（旧项目有独立 graph 但未与检索融合） |
| **重排** | ✅ `reranking.py`（286 行）cross-encoder | ✅ bge-reranker |
| **实测规模** | 面向"千级记忆单元" | 旧项目实测 1500 章 RAG 查询 **2.36s**、`rag_append` 20ms/章且线性 |

## 2. Hindsight 的检索栈（源码级）

```
engine/search/
  retrieval.py                809 行  语义+BM25 合并 SQL、时序合并、全类型并行
  link_expansion_retrieval.py 367 行  图扩展召回
  graph_retrieval.py           57 行
  bm25_term_selection.py       96 行  BM25 词项选择
  recall_boost.py              94 行
  fusion.py                   146 行  ★ RRF 融合（k=60）
  reranking.py                286 行  cross-encoder 重排
  temporal_extraction.py      116 行  时间表达抽取
  tags.py / trace.py / tracer.py
```

`fusion.py` 的实际实现确认了四路来源：

```python
source_names = ["semantic", "bm25", "graph", "temporal"]
# score(d) = sum_over_lists( 1 / (k + rank(d)) )   k=60
```

且 `cap_per_source()` 注释说明了工程细节：
**per-source 截断**，防某一路过度扩张挤掉其它路 —— 这是旧项目没有的考虑。

**这一层确实比旧项目强**：旧项目是纯 2 路 RRF（`hybrid.py:176 rrf_fuse`），
无图扩展、无时序、无 per-source cap。

## 3. 为什么**不能**拿它替代小说内检索（三个硬问题）

### 3.1 写入要过 LLM，规模上不可行

`retain` 走 `fact_extraction` + `consolidation`（**两次 LLM**）。
语料实测：`轮回乐园.txt` 39.79 MB、`剑来` 37.57 MB。
以 1500 章书为例，即使每章 1 次抽取，也是 **1500+ 次 LLM 调用**——
而旧项目/本项目的正文入库是**零 LLM**（本地 bge-m3 embed）。

> **成本对比**：本项目 P2 实测"输出占成本 77.5%"，
> 拿 LLM 来做"把正文变成可检索记忆"是把成本花在**基建**而非**生成**上，
> 与「质量优先」原则相悖（质量杠杆在生成侧，不在索引侧）。

### 3.2 语义错配：它抽的是"事实"，小说需要的是"片段"

`fact_extraction.py`（2526 行）抽的是**可陈述事实**（谁做了什么、何时）。
而小说检索的真实需求是**找回原文措辞**：
- 文风延续需要**原句**，不是事实摘要
- 伏笔回收需要**埋设时的原文**，不是"某人埋了伏笔"这条事实
- 「去 AI 味」的对照范本需要**真实文本**，不是改写后的事实

**事实抽取会丢掉措辞** —— 而措辞恰恰是小说质量的核心。
本项目 `scorecard/literal.py` 的比喻检测、套话检测、句长 CV **全部依赖原文**。

### 3.3 与既有账本重复，且无单一真相

本项目已有：
- `infra/storage/models.py`（16 张表，强外键）
- `domain/health.py` 伤势账本、`domain/entities.py` 实体/关系账本
- `WorldStateSnapshot`（地点/时间/在场/谁知道什么）

再引入一个 Hindsight bank 就是**第二套记忆真相** ——
这正是本项目反复踩过的"两处实现漂移"（枚举冲突 / `_classify` 与 CLI 口径分叉）。
且 Hindsight 的 bank 与书**不是一一对应**的自然映射（它是 agent 域的，不是书域的）。

## 4. ★ 真正有价值的用法：把「写作规范」做成可检索 bank

### 4.1 洞察

本项目**最贵的教训不在代码里，在文档里**：

| 现有文档 | 内容 | 现在怎么用 |
|---|---|---|
| `doc/07-工作方式与目标导向.md` §3 | 8 条反模式（静默降级/缺省即通过/只报告不阻断…） | **人工阅读** |
| `doc/交接文档.md` §5 | 4 类高频错误模式 + 4 条规程 | **人工阅读** |
| `doc/research/0X-*.md` | 8 份调研（10,782 行实测证据） | **人工阅读** |
| `00-决策记录.md` | D-01~D-16 决策与理由 | **人工阅读** |

**问题**：写作时（`chapter_writer` / `reviewer`）这些**完全没被注入**。
writer 节点只知道 prompt 里的通用文风规则，不知道
"本项目实测：比喻密度超标是 `ai_style` 首因（旧项目 228 条）"这类**项目自证知识**。

### 4.2 提议的用法（与小说检索正交，不冲突）

```
bank: storyforge::writing-craft        ← 跨书共享的写作规范库
        ↑ retain：把 scorecard 的实测结论、docs 的教训、审校 issue 归类
        ↓ recall：writer/reviewer 节点按当前章节特征拉取相关约束
```

**具体形态**：
- **写入**：每次 `score` 出新结论 / 审校产出 issue 归类 → retain 一条
  （例如"第 12 章比喻密度 3.2/千字 → 触发 ai_style"）
- **读取**：`chapter_writer` 组装 prompt 时，按 `beat_type` / 题材 / 已知问题
  recall 出 **3~5 条最相关的项目自证约束**，注入 semi_stable 层

**为什么这值得做**：
1. **闭环**：本项目已有 `scorecard`（度量）+ `aggregate`（触发）+
   审校（改写）—— 但**缺"把历史结论喂回生成"的那一环**。
   Hindsight 正好补这一环，且它的"跨会话记忆"定位与此**完全吻合**。
2. **不侵入**：bank 独立于 `books`，**不碰**任何既有账本 → 零耦合风险。
3. **低成本**：写入量是"每次评分 1 条"，不是"每章正文一次"。
4. **可验证**：A/B 可测（注入 vs 不注入，看 `ai_style` issue 数变化）。
5. **与 D-16 一致**：跨书共享 → 天然是多书验证的产物。

### 4.3 但必须说清：这是「锦上添花」，不是「必需」

诚实评估：**它提升的是"少犯已知错误"，不是"写得更好"**。
本项目当前最大的质量瓶颈是**链路还没跑通**（阶段 B 未完，
`write` 只产出 2 章正文），不是"缺一个记忆库"。

**排序建议**：放在**阶段 B/C 之后**，作为"质量闭环"的一个可选增强。
**现在做它 = 在链路未通时优化基建**，违反"一次一项、质量优先"。

## 5. 若要做，最小验证方案（先证伪再投入）

### 5.0 ★★ 实测结果（2026-09-17，已执行，非推测）

我没有停在"设计实验"，而是**真的跑了**。两个实验，两个决定性数字：

#### 实验 A/C 合并：retain + recall 全链路（bank `storyforge::craft-probe`）

**写入**一条写作规范（94 字）：

```json
{"items":[{"content":"【反模式】静默降级：读不到就返回空串/dict/0。
旧项目 read_chapter 静默返回空串导致正文丢失不报错。对策：读取失败必须抛错。"}]}
```

→ `success: true`，`usage: input 2998 / output 306 / total 3304`

**召回**（问"读取失败时该怎么处理？"）→ 返回 **6 条**，`type` 为
`observation` / `world` 各半。

**★ 决定性发现：原文措辞被摧毁。**

| 我写入的原文 | 召回返回的文本（实际） |
|---|---|
| 【反模式】静默降级：读不到就返回空串/dict/0。旧项目 read_chapter 静默返回空串导致正文丢失不报错。对策：读取失败必须抛错。 | ① "对策：读取失败必须抛错，以避免静默降级导致的正文丢失。"<br>② "对策：读取失败必须抛错。 \| 避免静默降级导致的正文丢失"<br>③ "静默降级是反模式：读取失败时返回空串/dict/0，会掩盖错误而不报错，导致问题无法及时发现。"<br>④ "旧项目的 read_chapter 静默返回空串，导致正文丢失且不报错，是静默降级反模式的实际案例。" |

**一条输入 → 被 LLM 拆成 6 条改写片段，且全部不是原句。**
这**实证了 §3.2 的语义错配**：Hindsight 的本质是"**事实抽取 + 归并**"，
它**刻意不保留措辞**。

> 对小说来说这是**致命**的：文风延续、伏笔原文回收、
> 「去 AI 味」对照范本，全都依赖**原句**。
> 而 `scorecard/literal.py` 的比喻检测、套话检测、句长 CV **全部读原文**。

#### 实验 B：边际成本（bank `storyforge::cost-probe`，拟合后已清理）

| 样本 | 内容字符 | input | output | total | 秒 |
|---|---|---|---|---|---|
| 短 | 27 | 2,968 | 86 | 3,054 | 3.9 |
| 中 | 135 | 3,028 | 85 | 3,113 | 2.0 |
| 长 | 675 | 3,328 | 96 | 3,424 | 3.0 |

最小二乘拟合 **`total ≈ 3,037 + 0.57 × 字符数`**

**★ 固定开销 3,037 tokens/次**（占短样本的 99%）——
即**每次 retain 都要付一次事实抽取 prompt 的钱**，与内容长度几乎无关。

换算：

| 规模 | 预估 token |
|---|---|
| 一章 5,000 字 | ~5,900 |
| 一本 1,500 章 | **~8,850,000** |
| 语料 266 MB（约 1.3 亿字） | **~153,000,000** |

**结论：批量灌正文在成本上不可行**（固定开销 × 章数是主导项）。

#### 两个实验的合并判定

| 路线 | 实测否决理由 |
|---|---|
| 正文入库当 RAG | ❌ ① 措辞被摧毁（实验 A）② 固定开销 3,037/章 × 1,500 章 ≈ 885 万 token（实验 B）|
| 写作知识库（§4） | ✅ **未否决** —— 写入量是"每条规范 1 次"，几十条量级；<br>且规范**本来就该被归并**（它要的是要点，不是措辞）|

> **所以 §4 的提议经实测存活，§3 的两条路线被实测否决。**
> 这正是"先证伪再投入"的价值 —— 省下了建一整套错误基建的时间。

### 5.1 若继续做写作知识库，仍需验证的一点

实验 A 也暴露了 §4 方案的一个**待解问题**：
召回返回 6 条高度重叠的片段（同一条规范被拆成 4~6 条）。
直接注入 prompt 会**稀释注意力**（本项目已因"一次抽太多"吃过亏：
旧项目单 prompt 抽 11 类 → `entity_classify` 空输出 100%）。

**因此 §4 落地时必须加"去重 + 限条数"**：
- 注入条数上限（建议 3 条）
- 按 `scores.final` 截断
- 或写入时就控制粒度（一条规范 = 一条 item，避免长文）

这一点在做之前要用实验确认可解，否则 §4 也只是"把噪声搬进 prompt"。

## 6. 与「题材抽象（阶段 C）」的关系

注意一个**顺序依赖**：
§4 的写作知识库要按**题材**区分约束（仙侠的"套话"与言情的"套话"不同）。
而**题材抽象（阶段 C）目前零代码**（`config/genres/` 是空目录）。

**因此顺序应是**：
```
阶段 B（跑通 write/score）
  → 阶段 C（题材抽象三层：Profile + 语义轴 + 契约测试）
    → 再考虑 Hindsight 写作知识库（有了题材维度，约束才有正确的分组）
```

若先做 Hindsight 后做题材抽象，会得到一个"**所有题材混在一起**的知识库"，
召回质量被稀释 —— 又要返工。

## 7. 最终判定（回答"能否排入计划"）

| 候选 | 能否排入 | 排在哪 |
|---|---|---|
| 用 Hindsight **替代**小说内检索 | ❌ **不排** | 定位错配（§3），且与既有账本重复 |
| 用 Hindsight 给**正文**做 RAG | ❌ **不排（已实测否决）** | 措辞被摧毁（实验A）+ 3,037 tokens/章固定开销（实验B）|
| 用 Hindsight 建**写作知识库**（跨书） | ⏸️ **可排，但排在阶段 C 之后** | 实测存活（§5.0）；但需先解去重/限条数（§5.1），且需题材维度（§6）|
| 自建 `infra/retrieval/`（书内检索） | ✅ **已该做** | 它是空的（0 字节），且 `hybrid.py` 的 2 路 RRF 可直接借鉴 |

> **最反直觉但最重要的一条**：
> 负责人问的是"用 Hindsight 优化小说检索"，
> 而实测结论是 —— **小说检索该自己写（现在还没有），
> Hindsight 该拿去做另一件事（写作知识库）**。
> 两者不冲突，但**不能互相替代**。
