# 03 · 分期实施计划

> **状态口径（2026-09-28）**：本文保存原计划和阶段验收历史，不再作为实时进度板；当前阶段、验证数据及下一步以 `doc/交接文档.md` 顶部快照为准。下方旧计划条目中的历史状态不得覆盖最新快照。

> **用途**：定义各期的目标、交付物、验收标准与依赖。是实际开发时的执行依据。
> **推进方式**：一期一个**单元化功能**，每期可独立验收、独立回滚。
> **约束**：遵循 `00-决策记录` 的有效决策。实时进度只维护在 `doc/交接文档.md` 顶部快照；本文件的状态列属于计划/历史记录，不要求每期同步更新。
> **验证规模**：一期 standard 档 20~30 章（D-04）。

### 关键设计决策（P0 阶段必须定死）

| 决策 | 内容 | 理由 |
|---|---|---|
| 章号 | **全书单一递增 int**（O-04） | 旧项目双表示导致 P0 事故 |
| 外键 | **必须建 FK** + `PRAGMA foreign_keys=ON` | 旧项目 0 FK、靠人工清单清理、漏过 6 张表；且 SQLite 默认**不强制** FK |
| 测试隔离 | 每个测试独立临时 DB（fixture 级） | 旧项目 121/123 个测试在模块级赋值 `os.environ` → 单进程 pytest 产生**假失败** |
| 观测字段 | `finish_reason` / `context_breakdown` / `cached_tokens` / `prompt_prefix_hash` 必采 | 旧项目 `finish_reason` 100% 缺失，导致 22.2% 空输出无法诊断 |
| 配置 | 单一入口 + 类型化 + **运行时注入**（非 import 期冻结） | 旧项目 26 个 JSON + 81 个 env + 7 个模块各自缓存 + `.env` 被 JSON 静默覆盖 |
| **节点幂等** | 以 `(book_id, chapter_no, node_name, attempt_no)` 为幂等键；重放时复用已有结果 | ⚠️ LangGraph **静默重放** >180s 的节点（`langgraph#7417`，53 评论仍 open）→ 2~3× 冗余成本。而旧项目实测 `editor` 平均 **117s**、`architect` **72s**，章节生成极易超 180s |
| **State 不可原地修改** | 节点必须返回新对象或用 reducer；并行分支不得写同一状态键 | ⚠️ `langgraph#8314` 状态通道**引用透传** → 原地改 state 会**污染调用方输入**（静默数据损坏） |
| **时间存 UTC ISO8601 字符串** | 不用 `datetime` 对象过 checkpoint | ⚠️ `langgraph#8826` datetime **静默丢时区** |
| 版本锁定 | 精确版本（不用 `^`/`~`）；**不 pin 1.0.x/1.1.x** | 1.0.x 声明 `langgraph-checkpoint<3.0.0`，与 checkpoint 4.x **互斥** |
| 依赖排除 | 不引入 `langchain-classic` / `langchain-community` / **`langgraph-supervisor`（已停维护）** | — |
| 结构化输出 | 优先 `json_schema` > `function_calling` > 避免 `json_mode`（中文长文本） | DeepSeek 官方承认 JSON Output "may occasionally return empty content" —— **可能正是旧项目 22.2% 空输出的成因之一** |
| **不依赖 LangGraph Store** | 长期记忆用自建表 | `SqliteStore` 官方明说 "not recommended for production" |

### 不做

- 不建业务表（只建 P1 需要的）
- 不写任何 Agent
- 不做 HTTP API
- 不接 LangSmith / 任何 SaaS（预留表与接口即可）

#### ⚠️ 痛点 5 的关键更正：光有「卷级台阶」不够

深度分析发现，痛点 5（1500 章困在一处）**不是"规划能力不足"，而是多层代码显式禁止横向扩张**：

| # | 旧项目位置 | 逐字原文 | 效果 |
|---|---|---|---|
| A1 | `architect.py:397` | 「每章 plot 必须是上一章情节的直接延续…**禁止每章自起自收（新场景开场+圆满收束）**」 | 禁新场景 |
| A2 | `architect.py:401` | 「**地点延续或自然过渡，禁止无交代的场景硬切或时间跳跃**」 | 禁地点跳变 |
| A4 | `architect.py:372` | 「ultra 档同一卷相邻章**必须场面连续**；**卷末可为下一卷换场留一句理由**」 | **换场只允许在卷末/卷首** |
| A5 | `writer.py:258` | 「禁止另起炉灶、禁止直接休息疗伤、**禁止无过渡换地图**」 | 写作层禁换图 |
| A6 | `editor.py:243` | 「**无过渡换地图仍须改写**」 | 审校层判为缺陷 |
| A7 | `writer_rules.py:374` | 「**禁止新增细纲之外的重要人物、重大转折、新功法/新设定/新地图**」 | 细纲没有 = 违规 |
| A8 | `editor.py:106` | 「无中生有的…**新地图**（剧情级加戏）→ 记「细纲偏离」」 | 换图记为偏离 |

**算术后果**：ultra = 3~6 卷 → 全书允许换地图的机会**只有 2~5 次**（卷首）。
书 23 = 400 章 / 5 卷 = **每 80 章才有一次换场许可**。

**地理熵实测**（从章 `plot`+`title` 抽取地点 token，比较前半本 vs 后半本）：

| book | 章数 | 后半本独有新地点 | 数量 |
|---|---|---|---|
| 24 | 447 | （无） | **0** |
| 23 | 400 | `裴照隔门`（非地名） | **1** |
| 18 | 350 | 5 个（全是已登场势力的变体） | 5 |
| 8 | 286 | `帝师府` | 1 |

书 23 的高频"地点"token 实测是：`周德海(11) 裴照隔门(9) 电梯在四楼(5) 长明楼(5) 陈砚下楼(5) 他上楼(4) 电梯门(4) 老周隔门(4) 他推门(3) ...`
> **400 章的故事，场景 token 的绝对主体是「门 / 电梯 / 楼层 / 走廊」。`长明楼` 是全书唯一地标，仅出现 5 次。**

**因果链闭环**：
```
禁新场景 + 禁地点跳变 + 写作/审校把换图判为缺陷 + 规划层无扩张 schema
→ 模型只能在同一地点内反复推进
→ 用「更细的描写 / 更多的心理独白 / 更多的重复场景」填章数
→ 这正是「过于啰嗦和 AI」的机械成因
```

**因此 P1 的硬性要求（P1-13）**：
1. **不得**继承 A1/A2/A4 的「章章必须无缝承接」绝对化表述 —— 改为「**默认承接，但允许规划好的换场**」
2. **不得**继承 A5/A7 的「禁止新地图」—— 改为「**细纲中规划的新地图正常写；细纲外的新地图才是加戏**」
3. **不得**继承 A6/A8 的「换图 = 缺陷」—— 改为「**无过渡的换图是缺陷；有过渡且在规划内的换图正常**」
4. `ChapterPlan` 需有字段标记本章是否为「换场章」（`is_transition`），供 lint 与审校区分对待
5. `structure_gate` 的 `location_reuse_ratio` 指标用于**在规划期**发现"某一地点占比过高"，而不是等到写作后

**目标**：把「质量」和「成本」变成**可量化、可回归**的数字。

> ⚠️ **重要优先级更正（基于实测成本归因）**
>
> 用户痛点 7 的表述是「token 预算分析优化缓存命中功能」。但实测成本结构显示缓存命中**不是最大的口子**：
>
> | token 类型 | 占比（Credits） |
> |---|---:|
> | hit（命中输入） | **0.35%** |
> | miss（未命中输入） | 22.15% |
> | **output（含 reasoning）** | **77.50%** |
>
> 反事实：`cache hit 44%→80%` 省 **13.96%**；`reasoning 降到 0` 省 **59.4%**。
> **但「砍 reasoning 长度」已被 74 条真实数据证伪**（配置上限从未撞到，收益≈0）。
>
> **因此 P2 的正确顺序是**：
> 1. **output 侧治理**（P2-7）：换模型档位 + 减少调用次数 + 消灭 blank 空转（**14.36% 的 token 是纯浪费**）
> 2. **定向补丁优先**（P2-9）：已实测省 **61.6%**，代价仅 −0.667 分
> 3. **缓存命中**（P2-6）：仍要做（省 8%~23%），但天花板约 40% 稳定段，且需先修 `bible_inject` 的按章裁剪

### 必须避免的四个成本口径缺陷（旧项目实测）

| # | 缺陷 | 新系统要求 |
|---|---|---|
| 1 | **reasoning 被重复计入**（`reasoning ⊆ completion` 但被相加）→ 成本函数多收 77% 输出费 | `reasoning_tokens ⊆ completion_tokens`，**不得相加** |

### 关键设计：三级流水线的质量约束

**正文严格串行**（一次一章）—— 这是 D-13 的硬约束。理由（旧项目实证）：

| 旧项目问题 | 后果 |
|---|---|
| 4 章并行起草时，上下文按**同一时刻账本**构建 | 后写的章**看不到前章记忆** |
| `_produce_first` 的 `join(timeout=1800)` 超时 | pregen 与 serial **双写同一章** |

**领先度限制**：正文最多领先细纲 **3 章**。
理由：旧项目 `kick_min_ready=3` 的意图正确（让正文有细纲缓冲），
但**不能无限领先** —— 否则细纲无法根据正文实际产出校正（正文跑偏了，后面 10 章细纲全部作废）。

### 关键设计：抽取为何拆三节点

旧项目单条 prompt **>10,000 字符**、一次抽 11 类信息：
- `entity_classify` 空输出 **100%**（32/32）
- `verifier` 空输出 **62.3%**
- 关系表被污染（86.7% 非人际关系）

新设计：
```
scene_extractor     → events + state_deltas（事实层）
entity_resolver     → 实体链接（新增/匹配既有）
relation_extractor  → 社会关系增量（只抽关系，不抽动作）
```
每个职责单一、输出强类型、失败可独立重试。

### 关键设计：抽取 prompt 的新规则（替代旧项目的「全量重报」）

**旧项目原文（禁止继承）**：
```
出场实体全量重报（防关系图空洞→下章无根出场）：
- 本章实际出场/被提及的每个角色、势力、地点、物品，都必须出现在
  relationship_updates 或 state_updates 中
```
**新规则**：
```
- 只报告发生变化的内容（新关系、关系转变、归属变更、状态变化）
- 明确区分 relations（社会关系）/ affiliations（归属）/ states（状态）/ events（事件）
- 「维持」状态不输出（持久化层自己保留）
- 动作（查看/记录/离开/拾取）→ 归入 events，不进关系
```

### 关键设计：审校不空转

旧项目实测：Editor 反复要求修改但从不产出可用 `revised_content`（`no_revised_content`、`too_short:3839<4600`、`no_improve:6->6`）→ 重写空转 → 原稿入库。

新设计的强制约束：
```python
class ReviewResult(BaseModel):
    issues: list[ReviewIssue]
    revised_content: str | None
    # model_validator: issues 非空 → revised_content 必须非空
    # 不允许「notes 里说了问题但 issues 为空」
```
且 `actions_taken` 由**代码**依据 `revised_content` 是否存在生成，**不采信模型自述**（旧项目实测模型在 notes 声称"已改写"而 `revised_content=null`）。

### 验收标准

```bash
uv run python -m storyforge.cli write --book <id> --chapter 1
# 单章完整闭环：组装→写作→打分→校验→（触发时）审校→抽取→提交
```

**P4 的硬性验收**：
1. 同一输入重复运行 → 打分卡结果**逐字节一致**（零 LLM 部分可复现）
2. 审校触发后，`revised_content` 非空率 ≥ 80%
3. 抽取三节点可独立失败重试，不互相牵连
4. 提交是单事务（构造失败场景验证回滚）
5. `finish_reason` / `context_breakdown` / `cached_tokens` 全部落库

### 缺陷 11 · 抽取阶段形状根治（2026-09-18）

上一轮实测 `write` 崩在抽取阶段（`state_updates.0: Input should be an object`）。
深挖后确认是**同一根因的三种表现**：

| # | 形状 | 现象 | 可见性 |
|---|---|---|---|
| F | `list[str]` | Pydantic 崩 → `write` 中断 | 可见 |
| G | `{"location": "+楼梯间"}` | 字段名被当成**实体名** | ★ **静默数据损坏** |

**根因**：抽取三节点 prompt **没有 JSON 骨架**（规划四节点有）。
项目自己记录过这条教训 —— `test_prompt_skeletons.py` 的 docstring 明写
「根因不是模型不听话，而是 prompt 只用散文描述字段，没给出确切骨架」——
但那份契约**只登记了 4 个规划节点，漏了 3 个抽取节点** → 契约全绿而缺陷存活。

**修法三层**：
1. **根治** —— 三个抽取 prompt 补 JSON 骨架（含 `state_updates` 的两种合法写法，
   并显式标注反例及后果）
2. **契约扩容** —— `STRUCTURED_NODES` 补入 3 个抽取节点（补契约漏洞本身）
3. **归一兜底** —— `list[str]` 拆条 + 字段名判据 + **字段分组**
   （`deaths`/`unsupported` 是名字列表，绝不能"拆条"）

**验证**：
- `scripts/mutate_extract_shapes.py` 三处真变异全部拦下 + 还原复验
- **真实 `write` 闭环首次跑通**：`第1章 OK 4706 字 / 5 次调用 / 空输出率 0.0%`
- 修复前后对照（同一章）：`entity='location'`（错）→ `entity='林默'`（对）
