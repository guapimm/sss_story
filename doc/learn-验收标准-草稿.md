## 1. ★ 溯源的真实状态（本标准的 P0 前提）

> ⚠️ **本节曾写错，2026-09-23 更正。**
> 初版写「带 source_urls 的 0/11」——那是**诊断脚本的 bug**
> （查 `source`/`source_url`，实际字段名是 `source_urls`）。
> 已修正脚本并重测。**这正是本项目记过的教训：诊断工具自身也会造假**
> （交接文档 §4.8）。下面的数字是修正后的实测值。

真实样本取证（书 991 / 宋代点茶 / fast 档 / 11 个知识点）：

```
知识点带 source_urls : 11/11 (100%)   ← 已实现
知识点带 evidence    :  0/11  (0%)    ← ★ 真正缺的
```

### 1.1 ★ "100% 溯源"有水分：11 条挂的是**同一组** URL

`commands/learning.py:469` 的实现与注释：

```python
# 溯源：知识点来自整份研究资料，不逐条对应某个 URL
# （模型只说"依据资料"，不指认具体是哪一条）
source_urls=tuple(str(s.get("url","")) for s in snippets if s.get("url"))[:3],
```

⇒ 每条知识点都挂**资料的前 3 条 URL**（样本里 11 条全是同一组：
维基百科 + nsteaset + zju）。

**这是「有来源」但不「可核验」** —— 无法回答
「**这条**知识点依据的是**哪一段**」。

⇒ 对验收而言：`source_urls` 非空**不足以**作为通过判据。

### 1.2 ★ `evidence` 被赋成了别的东西（语义错位）

同一处的 `evidence=shortfall or ""` —— 把「研究缺口提示」
塞进了本该放「支撑该知识点的原文片段」的字段。

`shortfall` 为空时 → `evidence` 全空，与实测 `0/11` 吻合。

**危害**：`validate_map` 只查"URL 非空"，所以这个错位**全绿通过**。
与项目反模式清单里的「**字段被赋成了别的东西**」同类 ——
比"没实现"更隐蔽。

### 1.3 为什么它是验收前提

没有**逐条**依据，判据不可执行：

  · "某个知识点错了"无法区分是**模型幻觉**还是**资料如此**
  · §4 的方案 B 核验**无法进行** —— 核验模型需要
    「知识点 ↔ 依据片段」的对应关系才能判断
    （`probe_verify_model.py` 能判准，正是因为手工喂了**编号资料**）
  · D-16「多书验证」的结论不可信

### 1.4 修法取向：结构化，不用启发式

| 方案 | 做法 | 评价 |
|---|---|---|
| **Ⓐ 模型标注（选定）** | `KnowledgePointOut` 加 `evidence_index`，prompt 里给资料编号 | ✅ 用户已确认 |
| Ⓑ 代码事后匹配 | embedding 算相似度取最高 | ❌ 启发式；项目已多次吃亏 |

**选 Ⓐ 的依据**（项目立的规矩）：

> 能用结构性事实回答的问题，不要用文本启发式回答。

`evidence` 是「**反幻觉的依据**」，必须是**可追溯的结构化事实**，
不能是相似度猜出来的。

### 3.1 ★ 研究达标率：**不设硬目标**（用户拍板）

实测：`standard` 档目标 25 个知识点，实际 6 轮（角度用尽）得到 ≈6。

**但这是正确行为** —— 设计上明确写着「**角度用尽如实报告缺口，不硬凑**」

**处置**：只**记录基线**（每次验收记录实际值），不设阈值，超标不告警。

## 4. ★ 知识准确性验收（方案 B：LLM 交叉核验）

用户选定方案 B。以下是建议的具体设计。

### 4.1 核验什么

对每条知识点，判断**是否被研究资料支撑**，输出三态：

| 判定 | 含义 | 处置 |
|---|---|---|
| `supported` | 资料里有直接依据 | 计入通过 |
| `inferred` | 资料未直说，但可由资料**合理推得** | 计入通过（但要标记） |
| `unsupported` | 资料里**找不到任何依据** | ★ 计入失败（疑似幻觉） |

**关键区分**：`inferred` 不等于 `unsupported`。
教学需要"把资料讲透"，合理推演是**必要的**（如由"点茶用茶筅"推出"茶筅是核心器具"）。
一刀切要求"逐字有据"会让地图退化成资料摘抄。

### 4.2 谁来核验（★ 防"自己批自己"）

**核心要求：核验侧必须与生成侧可区分**，否则等于自证。
但实测约束是 —— **当前只配了 `MIMO_API_KEY` / `TAVILY_API_KEY`**，
`DEEPSEEK_API_KEY` **未配置**，故**不能**用 DeepSeek 做核验。

三档方案，按"防自证强度"排序：

| 方案 | 核验侧 | 防自证强度 | 现在可用？ |
|---|---|---|---|
| **B1（推荐，已实测）** | `mimo-v2.6-pro` + 独立 prompt + 温度 0 | ★★ 换**模型档位**（pro vs flash），不同权重 | ✅ 可以 |
| B2 | 同模型（flash）+ 独立 prompt + 温度 0 | ★ 仅换 prompt，同权重仍有共谋风险 | ✅ 可以 |
| B3 | 异厂商（`deepseek-v4-pro`） | ★★★ 最强 | ❌ **缺 key** |

**建议先落地 B1，并保留升级到 B3 的口子**：

```
HINDSIGHT/核验模型从 providers.toml 读，不硬编码 ——
将来配上 DEEPSEEK_API_KEY，改一行配置即可升级到 B3。
```

| 项 | 生成侧 | 核验侧（B1） |
|---|---|---|
| 模型 | `mimo-v2.6-flash` | **`mimo-v2.6-pro`** |
| prompt | `LEARNING_MAP_SYSTEM` | 独立核验 prompt（**不复用生成 prompt**） |
| 输入 | 研究资料 + 主题 | **研究资料 + 生成的知识点**（模型看不到生成过程） |
| 温度 | `0.1`（抽取类） | **`0.0`**（判定要稳定可复现） |

> ✅ **B1 已实测可行**（`scripts/probe_verify_model.py`）：
> 喂 3 条知识点（2 条有据、1 条资料完全没提），
> `mimo-v2.6-pro` 在 800 / 4000 / 12000 三档预算下**全部返回**
> `[supported, supported, unsupported]` —— **判定准确，且区分力正常**。
> 800 档也没空输出（`providers.toml` 那条告警是特定 prompt 组合触发的，
> 非普遍行为）。故核验节点 `max_tokens ≥ 4000` 即可，留足余量。

> **B1 的诚实标注**：同厂不同档位**不是强隔离** —— 同一代模型可能共享训练数据与偏见。
> 本次实测只证明"**在明显案例上有区分力**"，不代表能抓住微妙幻觉。
> 因此 §4.3 的判据要留"人工抽检"作为最终防线，不能只信自动核验。


### 4.3 判据与门槛

```
准确率 = (supported + inferred) / 总知识点数
```

| 判定 | 条件 |
|---|---|
| 严格 | 准确率 **≥85%** |
| 硬门禁 | `unsupported` **不得连续 3 条**（集中幻觉比分散更危险） |
| 留痕 | 每条 `unsupported` 必须记录**模型给的驳回理由**，供人工复核 |

### 4.4 实现落点（复用已有结构，不另起炉灶）

| 步骤 | 落点 | 说明 |
|---|---|---|
| ① 接上溯源 | `graph/nodes/learning.py` | `generate_learning_map` 已收到 `snippets`，把 URL 按知识点回填到 `KnowledgePoint.source_urls` |
| ② 新增核验节点 | `graph/nodes/learning.py` | `verify_learning_map()`，仿 `check_gaps` 的两段式风格 |
| ③ 新增 schema | `infra/llm/learning_schemas.py` | `VerificationOut`（三态 + 理由） |
| ④ **登记契约** | `tests/contract/test_prompt_skeletons.py` 的 `STRUCTURED_NODES` | ★ **必须登记**，否则重演"无骨架而契约全绿"（已栽过两次） |
| ⑤ 落库 | 复用 `persist.py` 的模式 | 核验结果落盘供人工复核 |
| ⑥ 变异测试 | `scripts/mutate_*.py` | 证明"删掉核验就会红" |

- ① 是**唯一阻塞项** —— 没有溯源，核验无法定位依据
- ②~⑥ 依赖 ①

### 4.5 可复现性（沿用 golden 规则）

核验属 LLM 部分，**不做逐字节比对**，改为**断言性质**（与 §3 的 golden 规则一致）：
- 三态取值合法
- `unsupported` 必带理由
- 同一输入重复核验，**三态分布稳定**（允许个别条目抖动，但 `unsupported` 数不得翻倍）

## 5. ★ learn 不适用 story 的文风指标（必须显式声明）

现有 `05-验收标准.md` §1.2 的文风类指标，**对 learn 有害**：

| story 指标 | learn 为什么不适用 | 实测证据 |
|---|---|---|
| 对话占比 ≥25% | 教学章"**不要对话**"才是正确写法 | 标准说明文实测 `dialogue_low` **硬触发** |
| 套话命中 ≤2 | `综上所述` 是教学**标准连接词** | 被 `CLICHES:86` 判为套话 |
| 跨章 4-gram <6% | 教学需**重复强调**核心概念 | — |
| 比喻密度 ≤3 | 平替修辞**靠意象类比** | 样本中"凝茶术/炼茶仪轨"全是意象 |

### 5.1 建议新增章节

在 §1.2 之后新增：

```markdown
### 1.2.1 learn 模式的指标差异（★ 不得套用 1.2 的文风指标）

learn（教学小说）与 story（娱乐小说）的**质量维度不同**，
1.2 节的文风类指标（对话占比、套话、4-gram、比喻密度）
在 learn 下**不适用**：

  · 教学章「不要对话」是正确写法 → 对话占比下限会误判
  · 「综上所述」是教学标准连接词 → 套话检测会误判
  · 教学需重复强调核心概念 → 跨章重叠上限会误判
  · 平替修辞靠意象类比 → 比喻密度上限会误判

learn 使用独立维度集合，见 §3.2。
```

### 5.2 为什么这条比指标本身更重要

`style_critic.md` 的 6 项审查重点、`reviewer.py:55` 的 `CATEGORY_RULES` 8 类，
**全部是小说判据**。不改它们，learn 的每一章都会被判"不合格" ——
而且**判错的方向是"要求教学章像小说"**，会主动把内容改坏。

⇒ 这不是"少验收一项"，是**必须解除错误约束**。

### 5.3 知识点粒度（人工抽检项）

抽样 10 条，判读是否**可教**：

| 反例（太泛） | 正例（可教） |
|---|---|
| 「点茶定义」 | 「点茶与泡茶的三处工序差异」 |
| 「历史脉络」 | 「宋代点茶兴起与贡茶制度的关系」 |

**当前样本 11 条中有多条偏泛**（如「历史脉络」「历史影响」「技术要点」）
—— 这属于 §2-5 打分卡要解决的问题，此处仅作参考项记录。
