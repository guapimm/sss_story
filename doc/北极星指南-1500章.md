## 1. 最终产品标准

目标是让 story 模式能持续生成并管理约 1500 章小说，跨卷有因果推进、人物成长与关系变化，细节可信，文字不堆砌，失败时能停住、定位、恢复。**1500 是目标规模，不是本轮已证实能力。**

对读者，最重要的是每章有清楚的冲突目标、障碍、选择与代价；地点、势力、人物关系和知识状态随叙事合理扩展。段落不靠多写环境、反复动作、密集比喻或相似句式充字数。章末承接下一章，不凭空切场、失忆、伤愈或获知秘密。

对运营，长跑必须有确定的书/章状态、可重放证据、明确的暂停点、逐章成本与人工审读入口。提交后的正文是唯一权威版本；从最终正文抽取事实并入账，任何后续改稿都要使抽取失效并重做。旧草稿抽取不得代表已改动的最终稿。

五个互不替代的验收维度：

| 维度 | 需要看到的证据 | 不能代替它的东西 |
|---|---|---|
| 情节因果 | 目标—阻碍—选择—代价、伏笔与兑现、卷级升级，由人工盲读和结构账本共同核对 | 规划文件存在、自动总分高 |
| 人物连续性 | 状态、关系、伤势、已知事实、谎言、地点及时间前后可追溯 | 单章事实抽取有 JSON |
| 文风 | 喜欢/不喜欢样本的盲评偏好；审读注水、套式、无功能细节、对话自然度 | Editor 分数、4-gram、对话比例任一单项 |
| 稳定性 | 真实 CLI 入口、SQLite 行、checkpoint 恢复、重复执行幂等、失败可见 | `graph.compile()`、mock 调用全绿 |
| 成本 | 每章及每卷输入/输出/reasoning/缓存/重试 token，按实际模型单价核算 | 仅看 LLM 调用次数或理论缓存率 |

质量优先于节省 token。质量改善若增加成本，先量化增量再决定；不得因为省 token 而接受明显的因果或文风退化。

## 2. 当前系统的真实边界

### 2.1 已有的骨架

- **[源码]** `src/storyforge/graph/graphs/chapter.py:build_chapter_graph` 接上就绪、写作、打分、审校、定向修订、抽取、提交；`chapter_nodes.py` 分别实现节点。修订路径调用 `apply_revision_if_better` 复检，抽取节点重新读取正文文件，因此正常接线下是抽取修订后的最终稿。
- **[源码]** `ChapterState` 在 `src/storyforge/graph/state.py` 只持有有界上下文块与产物 ref；`ArtifactStore` 存大文本。`ChapterContext`、`assemble_context` 与 `memory_block` 已能表达前后状态锚、人物状态、关系、伤势、时间线、RAG、前章末尾。先接通数据生产与传递，别重造一套 prompt 框架。
- **[源码]** `src/storyforge/scorecard/literal.py` 已有章内冗余、跨章 4-gram、对话比例、套话、明喻、句长等指标；`aggregate.py` 已有路由。它们是告警和抽样工具，不能推出文学质量。`src/storyforge/graph/nodes/reviewer.py` 是审校与修订入口。
- **[源码]** `src/storyforge/graph/nodes/persist.py:persist_extraction` 可将抽取实体/关系落 SQLite，`chapter_nodes.py:make_commit_node` 使用它；提交状态仍须对 DB 与文件的真实一致性另做验证。
- **[源码]** `src/storyforge/graph/graphs/books.py:open_checkpointer`、`thread_config` 已存在；`graph/graphs/executor.py:GraphUnitExecutor.run` 传 thread 配置。存在工具不等于所有生产调用都接线。
- **[阶段记录]** `doc/交接文档.md` 当前摘要称 P0–P4、learn 2-1 至 2-6 完成，历史验收为 `1033 passed / 15 skipped`、doctor PASS、书 23 golden delta 0。**本轮没有重跑这些命令**；`doc/03-分期实施计划.md` 与 `doc/阶段2-进展报告.md` 的部分状态表已过期，以当前源码及新验收为准。

### 2.2 关键断点，按优先级处理

1. **上下文能表达，却没有从真实数据装配。** **[源码]** `src/storyforge/cli.py:_run_write` 调 `build_chapter_graph` 时初始 state 只填 `book_id/global_no/volume_no/detail_ready_through/refs/is_volume_end`。它没有填人物状态、关系、伤势、时间线、RAG、前章尾或下一章锚。`ChapterState` 没有 `relations_block`；`chapter_nodes.py:make_write_node` 没向 `write_chapter` 传 `relations` 或 `rag_snippets`。先证明真实写作 prompt 缺哪些块，再补同一个装配入口。
2. **章节恢复不能凭 thread ID 推断。** **[源码]** `build_chapter_graph` 以 `g.compile(name="chapter")` 结束，没有 checkpointer；CLI 传 `thread_config`，这本身不保存检查点。`open_checkpointer` 在 books 模块，但当前写作 CLI 未使用。真实 SQLite checkpoint 行、停机再启与幂等证据是必需品。
3. **没有完整的 run-book/resume 产品入口。** **[源码]** `cli.py` 可见 doctor/init-db/arch-check/score/baseline/plan/write/report，未见 `run-book` 或 `resume` 子命令；`src/storyforge/api/routes/__init__.py` 为空。`doc/05-验收标准.md` 所列 `run-book`/`resume` 是目标命令，不是当前可运行事实。
4. **最终稿与账本的不变量需落地。** **[源码]** `make_extract_node` 读取当前 `prose_key`，这是好基础；但需要在修改正文、进程中断、抽取失败、DB 部分失败、重复执行时检查 hash、ref、章节状态与账本是否一致。历史文档中的“原子提交”不能替代崩溃实验。
5. **文风指标易被误用。** **[阶段记录]** 旧书 23 的 47 章对话比例 p50 约 10.6%，旧项目许多 Editor 6 分和 must-fix 未消费；数值展示了问题，不证明 25% 是所有题材的健康硬线。对话可以服务冲突，也可能是水；比喻可以精准，也可能是堆砌。把这些指标留作可解释的取样线索与实验观察。
6. **1500 章 ultra 目标已定，配置仍冲突，是 P0 阻塞。** **[负责人本轮确认]** 仅 `story.ultra` 目标为约 7–8 卷、每卷 150–250 章，先规划全部卷升级台阶，卷末验收。**[后续实测修正]** `src/storyforge/domain/validators/structure_gate.py`、`config/settings.toml` 和 `volume_planner.py` 已改用相对占比，因为绝对 150–250 的全局闸门曾把合理的 400 章 × 4 卷 × 100 章误挡；标准档应保留这个修正。**[仍存冲突]** 当前全局 `volume_share_min=0.15` 使 ultra 的 7–8 卷数学上不可行；`config/scales.toml:[story.ultra]` 又写 3–6 卷、每卷 300–500 章、只细化首卷。需针对 ultra 对齐配置/校验/扩卷路径，不能对所有规模恢复绝对硬门禁。ultra 的目标偏离以有来源的验收报告和人工审核处理。

## 4. 最小系统形状：先把已有部件接通

```text
用户批准的书意图/题材与风格样本（尚待提供）
  → 已有 Bible / 卷规划 / 骨架 / 细纲
  → 章前读：权威章节状态 + 在场实体相关账本 + 前章出口 + 后章入口 + 有界证据片段
  → ChapterState 小字段 / ref → 写作 → 确定性告警 → 审校与定向修订/人工暂停
  → 以最终 prose hash 抽取 → 校验与提交 → SQLite 状态/文件/成本记录一致
  → 下章从已提交版本读取；定期做跨章、跨卷审计
```

**[建议]** 章前装配只新增一个清晰的调用点，先查看现有仓储 API 是否足够；把渲染/检索放在合适的既有职责模块。不要为了“更模块化”拆 `cli.py`、枚举或图节点；仅当可具体指出互不相关职责造成改 A 必须改 B 时才拆。`doc/07` 的 800 行是兜底红线，不是拆分触发器。

记忆分三层：稳定的圣经与卷目标、可变但需回溯的人物/关系/伤势/事实账本、章级最近事件与证据片段。注入时必须回答“此事实来自哪一章/哪一行账本、为什么与本章相关、是否已过期”；冲突时暂停或向人展示，不把旧事实静默覆盖。长 prompt 中间容易被忽略，因此限制条目数量、按本章任务排序，并测实际命中率；不要靠把全部历史塞进去解决遗忘。

节拍与扩张由现有规划实体及结构闸门承担；写作负责场景级兑现，章后检查负责计划与正文差异。**全书所有卷先有可验证的升级蓝图，场景细纲再按当前卷滚动生成**；“滚动细纲”不得偷换为“后续卷只有占位目标”。`story.ultra` 约 7–8 卷、每卷 150–250 章是本轮已确认的目标，允许写作规划依据情节提出有据偏离，并由验收和人工审核决定；不要变成所有 scale 共用的硬门禁。模型可以为文学效果偏离细纲，但关键里程碑、人物知识和状态变更必须留下可审查的原因与修订计划。避免让“严格逐句贴纲”压死人物行动的自然性。

## 5. 阶段路线图：一次只推进可独立验收的一段

### S0 证据基线与安全边界（先做）

**入口**：`cli.py` 的 `plan/write/report`、`graph/graphs/chapter.py`、`chapter_nodes.py`、`infra/storage` 与现有 `tests/unit/test_cli_flows.py`、`test_chapter_loop.py`。

**交付**：在隔离数据目录和单独书 ID 下，记录真实 CLI 参数、版本、运行时模型、调用与 token 日志、数据库表行、正文及抽取 hash、失败条件；把 `doc/05` 中不存在的命令标为目标。保存一份当前 story 章的 prompt 块清单与成本。不要动用户的 live books。

**验收**：全量 `uv run pytest`、`uv run storyforge doctor`、契约检查及书 23 baseline 口径复现，分别记日期、输出与失败原因；真实 `plan`/`write` 只在可控成本和隔离数据下运行。`1033/15/PASS/delta 0` 仅为历史参照，不能抄成新结果。

**止损**：环境或真实模型路由不明、生产书路径不明、不可隔离数据时停在只读诊断；不得为了“跑通”修改 live 数据。

**P0 结构冲突审计**：在 S0 同时沿 `doc/00` D-07 → `config/scales.toml` 与 `config/settings.toml` → 配置加载 → `VolumePlan/SeriesPlan` → `domain/validators/structure_gate.py` → `books.py` 卷规划/扩卷，列出原决策、标准档实测修正、当前默认值、测试和现有书兼容性。下一独立阶段仅对 ultra 做最小对齐，确保 7–8 卷可表达、标准档不回归，且“全卷蓝图、当前卷细纲”真正可用；未解决前不得声称 ultra 规划能支撑 1500 章。

### S1 真恢复与状态一致性（先于扩写）

**入口**：`books.py:open_checkpointer/thread_config`、`chapter.py:build_chapter_graph`、`cli.py:_run_write`、`chapter_nodes.py:make_commit_node`、`infra/storage/artifacts.py` 与 SQLite 仓储。查全部调用方后决定把 checkpointer 注入图的最小位置；不在 CLI 局部伪装恢复。

**交付**：真实 SQLite checkpoint 行可查；同一章在写作、修订、抽取、提交处中断后能按确定规则恢复，不重复提交。外部模型请求已发出但结果未知时，状态必须标为 `unknown` 并人工/账单核对，禁止自动重试；无法绝对保证零重复费用。清楚定义“已写文件但未入库”“已入库但状态未更新”“抽取缺失”时的修复动作。run-book/resume CLI 仅在此不变量明确后加入，复用现有调度/图，不另建平行编排器。

**验收**：一个真实 CLI 单章 + 强制中断/重启脚本，核对 SQLite checkpoint 行、章节/实体/关系行、产物 hash、LLM 幂等记录；重复启动后已提交章不新增调用，未知外部调用不自动重发。还要覆盖写作失败、空输出、C-7 人工暂停、DB 锁/不可用与文件写失败。先在隔离库验证，不能用“进程还活着”代表任务仍在执行。

**回退**：保留原 CLI 入口和旧行为的显式开关；恢复证据不全则只开放单章人工运行，不启动连续批跑。

### S2 上下文与事实账本闭环

**入口**：`cli.py:_run_write` → `ChapterState` → `chapter_nodes.py:make_write_node` → `chapter_writer.py:assemble_context` → `infra/prompts/library.py:memory_block`；仓储从 `infra/storage/repositories/` 查；如需检索，先评估 `infra/retrieval/` 现有能力与 story/learn 边界。

**交付**：按章从已提交数据装配前章出口、后章入口、在场人物状态/关系/伤势/时间线、相关伏笔和有限的前文证据。记录每块来源、字数/token、缺失原因；必需锚点缺失阻断，允许缺的块明确告警。只为真正要传的块新增 `ChapterState` 字段，如 `relations_block`；复用 `ChapterContext`/`memory_block`，不造第二个上下文对象。

**验收**：真实 CLI 写一章，保存脱敏后的实际 prompt 块清单和 SQLite 来源行；构造“角色未知秘密”“上一章受伤”“关系已改变”“前后章节换场”用例，确认错误被拦或进入人工待决。比对写入 token 和事实命中率。没有来源的 RAG 片段不可成为权威事实。

**回退**：逐块 feature flag；关闭新装配后回到 S1 可复现路径。若新旧差异影响事实正确性，先在 shadow 输出比较，不让 shadow 结果改账本。

### S3 场景兑现、文风校准与审校消费

**入口**：`domain/outline.py:ChapterPlan/SceneBeat`、`chapter_writer.py:render_plot_detail`、`scorecard/literal.py`、`scorecard/aggregate.py`、`nodes/reviewer.py` 以及 `chapter_nodes.py:make_review_node/make_revise_node`。

**交付**：以场景目的与因果链为审读单位，人工标记“必要细节/无功能细节”“动机不足”“重复动作/结构”“过密比喻”“套话”“对话解释替代行动”。Editor issue 要分级并被消费：事实、因果、连续性硬伤修复或人工豁免；风格项保留审读意见。正文改后重打分、重抽取、重校验 hash。绝不把 Editor 分数等同小说质量。

**样本门槛**：负责人稍后提供喜欢/不喜欢的章节，需尽可能给出题材、视角、篇幅、具体喜恶片段及可否直接用于内部评测。样本到来前只能测明显错误和结构性注水，不能宣称“已校准用户文风”。盲评时隐藏模型/版本，让至少两名审读者按事先冻结的 rubric 判断；分歧要记录。

**验收**：固定片段和新生成章节均做旧逻辑、新逻辑 shadow 比较；审校 issue 的未处理硬伤数、人工偏好、因果缺陷、稳定性、token 成本一起报告。任何自动阈值都先测误报和漏报，不为追指标强塞对话或禁尽比喻。

**回退**：样本不足、盲评无改善、事实错误升高或 token 失控时保持旧默认；新逻辑只留下可复查报告。

### S4 20–30 章低成本 canary，再逐级放大

**入口**：S1–S3 全部通过之后，用独立书/目录运行真实规划—写作—提交链。`doc/05-验收标准.md` 的 P5 标准可作目标清单，但用已实现的 CLI 命令；run-book 完成前可以用受控脚本顺序调用现有命令并留清楚断点。

**交付**：20–30 章的全链路数据、章节与卷目标映射、人工盲读样本、事实账本核对、每章 token/cost、空输出/重试/暂停/恢复报告。先固定一个题材与模型路由作 baseline；新逻辑经 feature flag → shadow → fixture 回归 → 质量和 token 对比，达标后才切默认，并保留 rollback。

**验收**：能从真实入口重启且无重写已提交章；每章最终稿 hash 对上抽取/账本；所有硬伤已处理或明确暂停；盲读未退化；成本有实测而非预算猜测。20–30 章只能证明局部闭环，**不能证明 1500 章稳定**。

**回退**：出现正文损坏、事实串书、未消费 must-fix、恢复重复扣费、连续空输出或质量显著退化，停止自动生成，保存证据并回到最后稳定 flag/书快照。不能自动“跳过坏章”继续。

**与原一期验收的关系**：`doc/05-验收标准.md` 明确一期只要求 20–30 章真实跑和 ultra 规划干跑，**不验收 1500 章真跑**。本指南的 S5 是负责人此次把最终目标提高到约 1500 章后的长期新增门槛，不把一期验收结论改写为长期能力证明。

### S5 多尺度压力与长期质量审计

按 **50 → 250 → 500 → 1000 → 1500 章** 逐级验证；每一级要有前一阶段已通过的真实数据，不能从小样本外推。若真实全量生成成本过高，可先用既有计划/模拟正文做结构和 SQLite 压测，但报告必须标明“模拟”，不能将其当文学质量证明。

| 规模 | 主要新增风险 | 最低证据 |
|---|---|---|
| 50 | 章间锚点、重复场景和短程人物状态 | 相邻章对照、人工抽读、状态账本完整性 |
| 250 | 卷级升级、地点/势力扩张、阶段性伏笔兑现 | 卷计划执行率、里程碑间距、跨卷状态审计 |
| 500 | 检索污染、别名合并、关系漂移、摘要失真 | 事实来源追溯、别名冲突审查、检索命中与误召回 |
| 1000 | checkpoint/SQLite 增长、恢复耗时、成本累积 | 恢复演练、库体积/延迟曲线、每百章成本与失败率 |
| 1500 | 全书因果闭合与读者疲劳、长期设定一致性 | 跨卷盲读、未兑现伏笔、角色成长、全书 token 与回退记录 |

每一级随机抽样之外，加看卷首/卷末、重大转折、停机恢复前后、关系或伤势变化章。比较新旧逻辑时题材、模型、路由、提示长度和人工评审规则应尽量固定；差异不可控时说明局限，不硬算提升率。25 章 canary 后用实测 token、实际模型单价、重试率给 50/250/500/1000/1500 章做区间成本预测，由负责人设置每阶段上限，越限即停并复核。D-05/P5 所需最小 HTTP API 与只读查看页可在 S1 状态/查询契约稳定后启动、S4 canary 中交付；完整交互 UI 后置，页面不能掩盖后端缺口。

## 6. 一票停机、回退与开放决策

立即停止自动写入的条件：最终正文与 extraction hash 不一致；已提交章被覆盖或重复扣费；跨书事实污染；必需章节锚点或状态缺失却被当通过；审校明确的关键事实/因果问题未消费；SQLite/文件部分失败却报告成功；模型实际路由与锁定路由不同；持续空输出或成本突破预设阶段预算。保存 book ID、chapter、配置、模型日志、产物与数据库快照后定位根因。人工批准不可逆人物消失和黄金三章等既有确认点，不能被批跑跳过。

回退顺序：停止新调度 → 保全产物和 SQLite 快照 → 核对最后一致的已提交章/hash → 关闭该阶段 feature flag → 在隔离数据中复现并修复 → 运行 fixture、真实入口、质量与 token 对比 → 再决定是否恢复。不要用 reset 或覆盖用户未提交工作来“恢复干净”。

需负责人决策且不替其拍板：首个 canary 题材/对照主题；提供喜欢与不喜欢样本的范围和使用许可；盲评参与者及接受/拒绝标准；每阶段可接受的成本上限、生成速度与人工确认频率；对必须暂停的重大人物命运/设定修改如何授权。技术实现中的阈值先由证据标定，再请负责人确认有实质影响的取舍。

## 7. 研究依据及外推限制

- **[论文]** [DOC（ACL 2023）](https://aclanthology.org/2023.acl-long.190/) 用分层详纲与控制器改善数千词故事的情节连贯与纲目对齐；支持本指南“规划+兑现”方向，**不证明 1500 章可控**。
- **[论文]** [Re3（EMNLP 2022）](https://aclanthology.org/2022.emnlp-main.296.pdf) 将计划、当前状态、相关前文检索和修订结合；启发章前事实选择与章后校验。实验是英文短长篇故事尺度，不能直接移植阈值。
- **[论文]** [DOME（NAACL 2025）](https://aclanthology.org/2025.naacl-long.63/) 探索动态分层详纲和时序图记忆；说明这些机制值得实验，不要求本仓库引入新图数据库或大框架。
- **[论文]** [Lost in the Middle（TACL 2024）](https://aclanthology.org/2024.tacl-1.9/) 发现长上下文不同位置的信息利用不均；支持有界、按相关性排序的注入，但未研究本项目 1500 章生成。
- **[论文]** [Lost in Stories（Findings ACL 2026）](https://aclanthology.org/2026.findings-acl.410/) 给出长故事一致性问题的分类，可用于设计审计样本；不等于可直接采用其指标或模型结论。
- **[论文]** [Help Me Write a Story（ACL 2025）](https://aclanthology.org/2025.acl-long.1254/) 显示 LLM 审稿可能漏掉重要问题；因此 must-fix 仍需人工抽检和后续事实验证。
- **[论文]** [LitBench（EACL 2026）](https://aclanthology.org/2026.eacl-long.362.pdf) 指出自动审美判断的可靠性有限；Editor 分数只用于分流，不作文学质量真值。
- **[论文]** [Catch Me If You Can?（Findings EMNLP 2025）](https://aclanthology.org/2025.findings-emnlp.532/) 提示少量例子模仿个人文风并不稳健；用户样本到来后仍需盲评和迭代。上述研究多数在数千词英文等远短于 1500 章的条件下验证；规模结论必须由本项目真实长跑逐级建立。
