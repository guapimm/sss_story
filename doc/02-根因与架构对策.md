## 对策 ① 一等实体模型：关系 / 交互分离

### 实测问题

旧项目的 `relationships` 表**同时承担三种语义**，导致全部失真：

1. **真正的社会关系**：师徒、敌对、血亲 —— 仅 98/739 = **13.3%**
2. **实体归属/位置**：`陈砚 <-值守-> 档案馆`、`值夜牌 <-门禁通行绑定-> 值夜室`
3. **动作流水账**：`查看`、`记录`、`离开`、`拾取物品`、`值班`

**直接成因**（`app/agents/post_processor.py` L74-81，原文）：
```
出场实体全量重报（防关系图空洞→下章无根出场）：
- 本章实际出场/被提及的每个角色、势力、地点、物品，都必须出现在
  relationship_updates 或 state_updates 中；
- 已存在的关系本轮未变化也要显式输出一条 status="维持"（仅确认不重复建边）；
```
配合「17 类端点组合」的指令，抽取器被迫把**每一次物品接触**都写成关系。

### 架构对策

#### 1.1 实体是独立的表，不是字符串

```python
class Entity(BaseModel):
    id: int
    book_id: int
    kind: EntityKind          # CHARACTER | FACTION | LOCATION | ITEM
                              # | TECHNIQUE | RULE | TERM | EVENT
    canonical_name: str       # 正名（唯一）
    aliases: list[str]        # 别名（含旧称、尊称、代号）
    first_seen_chapter: int
    # kind 专属属性放 JSON 列（Pydantic 校验后写入）
    attributes: dict
    is_active: bool
```

**关键**：`Entity` 有 **ID**。所有其他表引用 ID，不引用名字。这解决：
- 地点碎片化（`长明楼三层值班室` / `长明楼三层走廊` / `长明楼三楼档案科资料室` → 同一 Location 实体 + 层级结构）
- 名字漂移（旧项目实测「楚渊 → 萧尘 ×412」）
- 生命周期前缀解析（`[毁·可修]青锋剑` 应解析为「实体 `青锋剑` + 状态字段 `destructible_damaged`」，而非把前缀塞进名字）

#### 1.2 三张表替代一张表

| 表 | 语义 | 示例 | 更新方式 |
|---|---|---|---|
| `entity_relation` | **社会关系**（有情感/立场/权力语义，会演化） | 师徒、敌对、血亲、盟友、上下级 | 有 `since_chapter`、`status`，可演化 |
| `entity_affiliation` | **归属**（成员关系，可多重） | 陈砚 ∈ 档案馆夜班；陆知白 ∈ 七夜社 | 有 `joined_chapter`、`left_chapter` |
| `entity_state` | **实体自身状态**（位置、持有、损伤、境界…） | 陈砚.位置 = 长明楼值班室 | 字段级更新，带 `updated_chapter` |

**`交互（interaction）` 不再是关系** —— 它是 `story_event` 的一部分。`陈砚查看录音笔` 是一条 **event**（有 chapter、location、participants），不是关系。

#### 1.3 势力必须是一等实体

实测：势力实体 **0 个**。这是「势力归属乱」的根因。

新模型：
```python
class Faction(BaseModel):
    entity_id: int
    tier: FactionTier         # 顶级 / 大宗门 / 地方势力 / 地下组织 / 家族
    power_level: int          # 可量化的势力强弱（随剧情演化）
    home_location_id: int | None
    ideology: str             # 立场/理念（决定与其他势力的关系倾向）
    resources: list[str]      # 掌握的资源/秘宝/功法
    is_active: bool           # 覆灭后置 False（对应旧 `[灭]` 前缀）
```

**势力强弱可演化** —— 这是长篇结构丰满度的关键：主角换地图时，新地图的势力格局要与旧地图**不同**（更强的对手、不同的规则）。

#### 1.4 地点必须层级化

```python
class Location(BaseModel):
    entity_id: int
    parent_id: int | None     # 层级：世界 > 国家 > 城市 > 建筑 > 楼层 > 房间
    level: LocationLevel
    geography_tags: list[str] # 气候/地形/繁华度（影响描写与事件类型）
    controlling_faction_id: int | None   # 当前控制势力（可变）
    is_accessible: bool       # 是否可达（封锁/毁灭）
```

层级化解决两件事：
1. **碎片化**：`长明楼三层值班室` 与 `长明楼三楼档案科资料室` 都归到 `长明楼/三层` 之下，可查询"三层有哪些房间"
2. **长篇扩张可量化**：可直接统计"第 N 卷新增了多少个 Location"，作为硬闸门指标

#### 1.5 抽取 prompt 必须重写

**禁止**「全量重报」。改为：
- 只报告**发生变化**的内容（新关系、关系转变、归属变更、状态变化）
- 明确区分：`relations`（社会关系）/ `affiliations`（归属）/ `states`（状态）/ `events`（事件）
- 「维持」状态**不输出**（持久化层自己会保留）

同时引入**实体解析（entity resolution）**独立环节：把新提到的名字/地点/物品对到既有实体，或创建新实体。这是独立的一步，不塞进抽取 prompt。

### 验证指标

| 指标 | 旧项目实测 | 目标 |
|---|---|---|
| 人物-人物关系占关系总数 | 13.3% | **≥ 60%** |
| 势力实体数量 | **0** | ≥ 4（对齐旧 `ultra_structure` 设计要求）且随卷增长 |
| 地点实体归一率（同指合并） | 40+ 变体未归一 | 未归一新变体 ≤ 5% |
| 角色被追踪数 / 出场角色数 | 18 / 数百 | ≥ 80% |

## 对策 ② 长篇结构：卷级升级台阶前置

### 实测问题

```
书23  chapters: 400 → 卷分配 {1: 400}     ← 全部第 1 卷
      volumes[1..4].blueprint = "missing"
      volumes[3..4].main_line = ""
      plot_nodes: 仅 4 个（要求 ≥9）
      story_events.location: 长明楼/档案馆占绝大多数

书24  chapters: 447 → 卷分配 {1: 447}
      volumes[0..2].main_line = ""
      vol_end_hook 卷2 = "推向「首次记忆剥夺」的下一个阶段"  ← 模板化填充
```

**成因链**：
1. `backend/scales.json` → `story.ultra.rule`：**「本次只细化第 1 卷」**；`per_vol: 300~500`
2. `agents/architect.py` `_normalize_blueprint_volumes()`：后续卷缺失 → **补占位卷 + 标 `blueprint="missing"`**
3. 模型把 total_chapters 全部分配给第 1 卷（因为只有第 1 卷需要细化）
4. 第 1 卷的 `vol_goal` 是「在长明楼读透三十七条」→ **400 章全在一栋楼里**

**致命之处**：书 23 的大纲**规划质量其实很高**（5 卷台阶清晰：长明楼→城市节点网→租界→立约人→拆制度；8 个段落目标各有独立冲突）。问题不在创意，**在于「只细化第 1 卷」这条规则让升级台阶从未进入生成流程**。

### 架构对策

#### 2.1 卷 = 完整升级台阶（强制字段）

```python
class VolumePlan(BaseModel):
    volume_no: int
    title: str
    # ── 台阶定义（缺一不可，由 schema 强制）──
    new_locations: list[str]        # 本卷新开地图（≥2，且不得与已用地图重复）
    new_factions: list[str]         # 本卷新登场势力（≥2）
    antagonist: str                 # 本卷主要对手（必须与上卷不同）
    power_ceiling: str              # 本卷力量/能力上限
    core_conflict: str              # 本卷核心矛盾
    escalation_from_prev: str       # 相对上卷「升级在哪」（必须具体）
    # ── 收尾 ──
    old_map_closure: str            # 旧地图如何收尾（不是弃置，是有交代地离开）
    volume_end_hook: str            # 卷末钩子
    # ── 规模 ──
    chapter_budget: int             # 本卷章数（150~250，见 D-07）
    milestones: list[Milestone]     # 里程碑（≥ volume.chapter_budget / 25）
```

**关键设计**：`new_locations` / `new_factions` / `antagonist` / `escalation_from_prev` 是 **required 字段**。模型无法通过"省略"来逃避扩张设计。若模型给不出，schema 校验失败 → 重试或触发修复子图（对应旧项目 `ultra_structure_repair` 的增量补缺思路）。

#### 2.2 两阶段规划：台阶全定 → 单卷细化

```
阶段 A（一次）：全卷升级台阶
  输入：主题、题材、总章数目标
  输出：VolumePlan[]（全部卷，每卷含 above 全部字段）
  校验：扩张度闸门（见 2.3）
  ⚠️ 此阶段不产出任何章节级大纲

阶段 B（每卷一次）：当前卷细化
  输入：本卷 VolumePlan + 前情摘要
  输出：Segment[] + ChapterPlan[]
  ⚠️ 细化时必须遵守 VolumePlan 的 new_locations / new_factions / antagonist
```

这直接消除旧项目的缺陷：**升级台阶在阶段 A 就全部定稿并校验通过**，不存在"后续卷 blueprint missing"。

#### 2.3 扩张度硬闸门（结构校验器，必须 enabled）

旧项目 `ultra_structure_config.json` 的指标**设计正确但未启用**（`enabled: false, shadow: true`）：
```json
{ "min_arcs": 6, "min_core_arcs": 2, "min_relationship_arcs": 2,
  "min_opposition_arcs": 2, "min_beats_per_arc": 8, "max_beats_per_arc": 20,
  "min_arc_capacity": 300, "min_milestones": 9,
  "min_factions": 4, "min_characters": 3, "min_volumes": 3 }
```

新系统**继承这些指标并强化**，关键新增：

| 新指标 | 定义 | 为什么 |
|---|---|---|
| `location_growth_rate` | 每卷新增 Location 实体数 / 卷章数 | 直接防「困在一处」 |
| `faction_growth_rate` | 每卷新增 Faction 实体数 / 卷章数 | 防势力格局停滞 |
| `location_reuse_ratio` | 单卷内最高频地点的事件占比 | 旧书 23 此项极高（长明楼占绝大多数） |
| `milestone_density` | 里程碑间隔最大值 ≤ 25 章 | 旧书 23 有 **202 章里程碑真空**（3→205） |
| `antagonist_distinctness` | 各卷 antagonist 两两不同 | 防同一对手贯穿全局 |
| `escalation_concreteness` | `escalation_from_prev` 不得为模板句 | 旧书 24 出现「推向「X」的下一个阶段」模板句 |

**闸门必须在 `enabled: true` 状态运行**，且失败**阻断**（不是 shadow）。旧项目的教训是校验器设计对了却关着，等于没有。

#### 2.4 章节级：细纲必须含场景骨架

旧项目已有良好设计（`flowmode/base.py` `_detail_block` 要求细纲是「场景/人物：目标→阻碍→结果」的分场景拍点表），以及**前后锚点**机制（`prev_exit_state` / `next_entry_state`）。这些要继承并强化为 schema：

```python
class SceneBeat(BaseModel):
    location_id: int
    participants: list[int]        # entity ids
    goal: str                      # 谁想做什么
    obstacle: str                  # 阻碍
    outcome: str                   # 结果
    why_now: str                   # 为什么是现在（必须由上一拍结果逼出）

class ChapterPlan(BaseModel):
    chapter_no: int                # 全书单一递增（O-04）
    volume_no: int
    segment_no: int
    title: str
    beat_type: BeatType            # OPENING/TURNING/CLIMAX/BOSS/EMOTION/RECALL/NORMAL/SETTLE
                                   # ★ 必须含 HEAL / RECOVERY_PREP（旧项目 VALID_BEATS 缺失）
    is_transition: bool            # ★ 是否换场章（供 lint/审校区分对待，解决换图禁令问题）
    scenes: list[SceneBeat]        # ≥ 4
    entry_state: WorldStateSnapshot # 地点/时间/在场人物/谁知道什么
    exit_state: WorldStateSnapshot
    plant_foreshadowings: list[str]
    resolve_foreshadowings: list[str]
    health_beats: list[HealthBeat] # ★ 见对策 ④
```

**注意** `entry_state` / `exit_state` 必须是**结构化** `WorldStateSnapshot`（含 `location_id` / `time` / `present_entity_ids` / `known_facts`），而非旧项目的自由字符串。

**实测证据（证明为什么必须结构化）**：
- 旧项目 `entry_state` 填充率**仅 13%**（段1=100% → 段2=12% → 段3起**归零**）
- `plot_detail` p50 **788**，低于下限 900
- `milestone_ids` 落地率 **0%**
- `conflict_curve` / `character_arcs` 在 prompt 里要求了，**代码从不校验、不落库**

结构化后：
- lint 可**机械校验** `exit_state[N] == entry_state[N+1]`（旧项目只能做自由字符串比对）
- 可直接算出"上一章谁在场、这一章谁在场"的连续性
- 可直接检测「伤势角色是否在场景中被合理处理」

## 对策 ⑧ 「要求 ≠ 执行」的系统性防治（跨切面约束）

### 实测问题

旧项目存在**系统性的失效模式**：prompt 里写了要求，代码从不校验、不落库，导致**静默失效**。

| 字段 | prompt 要求位置 | 实际落地 |
|---|---|---|
| `entry_state` | `architect.py:1806-1808` | **13%**（段1 100% → 段3起 0%） |
| `plot_detail` 下限 900 | `outline_config.json` | p50 **788**（未达标） |
| `milestone_ids` | 大纲 schema | **0%** |
| `conflict_curve` | `architect.py:413-414`（唯一出现处） | **从不校验、不落库** |
| `character_arcs` | 同上 | **从不校验、不落库** |
| 伏笔配额 | `foreshadow_prompt_block` | 配额要 3 个 boss，实产 **41 个** → 配额完全不起作用 |

**同型 bug 只修一处的案例**：
> `continue_story.py:1251-1259` 是与 `_synthesize_segments` **完全同型**的活 bug ——
> Python 列表推导给每个续接卷写入**逐字相同**的 goal。
> 2026-09-11 修了**分段**的同句问题，**没人检查续卷的同一处**。book 11 实测三卷逐字相同。

**活着的逻辑矛盾**：
> `min_milestones ≥ 9`（配置）vs `_clean_milestones` 的 `ms[:8]`（`story_director.py:494`）
> —— 要求 9 个但代码截断到 8 个。因 `enabled: false, shadow: true`，矛盾从未暴露。

### 架构对策：三条强制机制

#### 8.1 每个"要求"必须有一个"断言"

```
规约：prompt 里出现的任何数量/结构要求，必须同时存在于
     ① Pydantic schema（必填字段或 validator）
     ② 校验器（lint / gate）
     ③ 单元测试（断言该要求会被检出）
否则该要求**不得写入 prompt** —— 因为没有校验的要求就是噪声。
```

**实现**：`tests/contract/test_prompt_requirement_coverage.py`

```python
def test_every_prompt_requirement_has_a_validator():
    """扫描所有 prompt 模板中出现的数量约束（如「≥4 个场景」「9 个里程碑」），
    断言每个都有对应的 validator 与测试。"""
    requirements = extract_numeric_requirements(PROMPTS_DIR)   # 正则 + 结构化提取
    validators = collect_validators(DOMAIN_VALIDATORS_DIR)
    for req in requirements:
        assert req.key in validators, (
            f"prompt '{req.prompt_file}' 要求 {req.key}={req.value}，"
            f"但没有对应校验器 —— 这会导致静默失效（旧项目实测 13%/0% 落地率）"
        )
```

#### 8.2 结构化优先于自由文本

| 旧项目 | 新系统 | 理由 |
|---|---|---|
| `entry_state` 是自由字符串 | `WorldStateSnapshot` 对象 | 自由字符串**无法机械校验**（旧项目只能做字符串比对，且实测 13% 落地） |
| `participants` 是 JSON 数组存字符串名 | `event_participants` 关联表存 `entity_id` | 旧项目实测 `participants` 大量为空数组（书 23 第 1 章全空） |
| 生命周期前缀塞在名字里 `[毁·可修]剑` | 实体状态字段 | 名字解析脆弱（旧项目需专门写 `_strip_life_prefix`，且顺序敏感） |
| 章号 `vol*10000+idx` | 单一 `int` | 双表示导致 P0 事故 |
| `relation_type` 是自由文本（40+ 种） | `RelationKind` 枚举 | 自由文本导致「归属」vs「所属」互相删除 |

#### 8.3 shadow 模式必须有退出期限

```
规约：任何 shadow 模式的校验器，必须在 N 次运行内（默认 20 次）产出
     明确的「切换到阻断」或「放弃」决策并记录。
禁止：长期停留在 shadow（旧项目实测：ultra_structure 与 outline_lint
     均长期 shadow，导致 400 章挤一卷、412 项 lint error 全部放行）。
```

**实现**：`domain/validators/shadow_registry.py` 记录每个校验器的 shadow 起始时间与运行计数，
超期未决策则在**启动日志**与**报告**中显著告警（不是硬失败，但要可见）。

#### 8.4 每个信号必须有消费者（★ 旧项目最严重的单点缺陷）

**实测**：`must_review` 是**只写不读的死信号** —— 全仓 **25 个命中、0 个读取点**。

```
唯一近似读取：pipeline.py:6301 把它写进 trace metadata
_commit_chapter(..., must_review, ...)（pipeline.py:7122）收进形参后再未引用
真正闸门读的是另一条链：_force_flags = bool(style_notes) or _is_turning（pipeline.py:7354）
```

**后果**：`style_metrics.needs_rewrite` 的全部"阻断"语义，
**实际强度 = 强制调用 Editor 一次 + 加一段警告**。
Editor 返回 `revised_content: null`（`editor.py:319` 明文允许）→ **正文一字不改入库**。

**这不是个例，而是系统性模式**。同类证据：

| 信号/机制 | 写入处 | 读取处 |
|---|---|---|
| `must_review` | 25 处 | **0 处** |
| `prose_style.analyze()` | 有实现 | 只进 trace metadata（`shadow: true`） |
| `outline_lint` | 412 项 error 检出 | `enabled: false` → 放行 |
| `detail_review.py` | **7,042 字符 prompt + 1,273 行检查器** | **零生产调用者** |
| `must_review` / `style_metrics` | 检测到 185/210 章（88.1%）有文风问题 | **57~60 章仍判 passed** |
| `pacing`（流派画像） | 有定义 | **零消费点** |
| `state_schema` / `extra_entity_types` / `extra_relation_pairs` | 有定义 | **零生产消费点** |
| `experiment` 字段 | 3 处写入 | **无任何代码读取** |
| `conflict_curve` / `character_arcs` | prompt 要求 | **从不校验、不落库** |
| `milestone_ids` | schema 有 | 落地率 **0%** |
| `entry_state` | prompt 要求 | 填充率 **13%** |

**架构对策：三段式规约**

```
规约 A（生产者）：任何写出的信号，必须在同一 PR 内指明其消费者
规约 B（消费者）：任何"检测/评分/校验"必须终结于三种结局之一：
                 ① 阻断（改变流程）
                 ② 落库（可查询、可报告、可回归）
                 ③ 显式声明为"仅观测"并记录在 shadow_registry
                 不允许存在第四种：「写进日志就没人看」
规约 C（验证）：AST 检查 —— 每个 `must_*` / `needs_*` / `_flags` 形式的变量
                必须有读取点，否则测试失败
```

**实现**：`tests/contract/test_signal_has_consumer.py`

```python
def test_no_write_only_signals():
    """检测只写不读的信号变量。旧项目 must_review 25 处写入 0 处读取，
    导致整条文风控制链失效。"""
    for var in collect_signal_variables(SRC):          # must_*, needs_*, *_flags, *_enabled
        writes = count_writes(var)
        reads  = count_reads(var)                      # 排除写入语句本身
        if writes > 0 and reads == 0:
            pytest.fail(
                f"信号 '{var}' 有 {writes} 处写入但 0 处读取 —— "
                f"这是只写不读的死信号（旧项目 must_review 的复现）"
            )
```

> **这条是本项目从旧项目学到的最重要教训之一**：
> **检测能力不缺，缺的是执行通道。**
> 旧项目 Editor 甚至抓到了「比喻」43 次并给出改写建议，而代码层"比喻"零实现 ——
> 说明 LLM 语义审校能发现的问题，**确定性代码抓不到也不该抓**，
> 关键是**让已有的 LLM 结论真正驱动流程**，而不是再加检测器。

## 对策 ⑨ 记忆预算必须随篇幅增长（最底层成因）

### 实测问题

旧项目各记忆块的字数上限是**恒定常量**：

| 记忆块 | 上限 | 来源 |
|---|---|---|
| 前情时间线 | 6,000 字 | `memory.py:1680` |
| 世界观圣经 | 4,200 字 | `bible_inject.py:37` |
| RAG 前文片段 | 1,800 字 | — |
| 前卷摘要 | 200 字/卷 | — |

```
→ 记忆密度随篇幅衰减：
   第   50 章：12,000 字 /  25 万字 = 4.8%
   第 1500 章：12,000 字 / 750 万字 = 0.16%
```

> **第 1 章与第 1500 章拿到的世界记忆一样多。**
> 到后期只有 0.16% 的可用带宽 → **模型唯一能做的就是把当下这一小片场景反复描摹到字数达标**。
> **这才是「过于啰嗦和 AI」的最底层机械成因**（换图禁令是放大器）。

### 架构对策：分层摘要 + 动态预算

#### 9.1 分层摘要结构（替代恒定文本累积）

```python
class MemoryHierarchy(BaseModel):
    """记忆必须按「距离」分层压缩，总预算随篇幅增长。"""
    recent_chapters: list[ChapterSummary]      # 近 N 章：全文级细节
    arc_summary: str                            # 本 arc 摘要
    volume_summary: str                         # 本卷摘要
    series_summary: str                         # 全书（前序卷）摘要
    key_facts: list[KeyFact]                    # 结构化关键事实（永久保留）
    active_threads: list[Thread]                # 活跃线索/伏笔
```

**压缩策略**：
```
章级细节 → 每章保留全文（用于近 N 章的 prev_prose）
         → 超出 N 章后压缩为 arc_summary
arc 级   → 每 arc 保留摘要
卷级     → 每卷保留摘要
全书     → series_summary 递归压缩
```

#### 9.2 预算随篇幅增长（不是恒定）

```python
def memory_budget(chapter_no: int, total_chapters: int) -> MemoryBudget:
    """记忆预算必须随篇幅增长，保持记忆密度不衰减。
    
    旧项目恒定 12,000 字 → 密度从 4.8% 衰减到 0.16%。
    新设计：预算随 log(篇幅) 增长，使密度维持在合理区间。
    """
    # 基准 + 对数增长（避免线性膨胀导致上下文爆炸）
    base = 12_000
    growth = int(base * 0.5 * math.log2(max(1, chapter_no / 50) + 1))
    budget = base + growth                      # 50章:12k, 200章:18k, 400章:21k, 1500章:27k
    return MemoryBudget(
        total=budget,
        timeline=int(budget * 0.20),
        states=int(budget * 0.25),
        rag=int(budget * 0.15),
        summaries=int(budget * 0.25),           # ★ 新增：分层摘要
        other=int(budget * 0.15),
    )
```

**验证指标**：

| 指标 | 旧项目 | 目标 |
|---|---|---|
| 记忆密度 @ 第 50 章 | 4.8% | ≥4% |
| 记忆密度 @ 第 500 章 | ~0.5% | ≥1.5% |
| 记忆密度 @ 第 1500 章 | **0.16%** | ≥0.8% |
| 密度衰减倍数（50→1500 章） | **30×** | ≤5× |

### 为什么这条很重要

`02` 的其他对策（卷级台阶、换图正向机制、扩张闸门）解决的是**"故事应该去哪里"**。
这条解决的是**"模型有没有能力写到那里"**。

> **若记忆预算恒定，即使规划了 7 卷新地图，模型在第 500 章之后也没有足够的世界记忆
> 去写一个"新"的地方 —— 它只知道当下这一片场景。**
> 两者必须同时做，缺一不可。

## 对策 ③ 关系张力模型（解决痛点 4）

### 实测问题

- 人物-人物关系仅 **98/739 = 13.3%**
- 仅 **18 个角色**被追踪（400 章的小说）
- `relation_type` 分布扁平：`同门25 / 师徒24 / 盟友21 / 上下级13 / 敌对11 / 亲属11 / 血亲9` —— **全是静态标签，无张力维度**

**「人物关系单一」的本质**：关系被降维成一个**名词标签**，没有：
- 强度（亲密/疏远程度）
- 双向性（A 对 B 的信任 ≠ B 对 A）
- 张力（表面 vs 真实立场）
- 演化（什么事件让关系变化）

### 架构对策

```python
class EntityRelation(BaseModel):
    id: int
    book_id: int
    from_entity_id: int
    to_entity_id: int
    relation_kind: RelationKind   # 社会关系类型（师徒/敌对/血亲/盟友...）
    # ── 张力维度 ──
    intensity: int                # 0~100 强度
    sentiment: Sentiment          # 正面/中性/负面/矛盾
    # ── 明暗分离（继承旧项目正确设计）──
    surface_facing: str           # 世人所知的关系表现（对应旧 visibility=明）
    true_facing: str | None       # 真实立场（对应旧 visibility=暗）
    # ── 演化 ──
    since_chapter: int
    status: RelationStatus        # ACTIVE / CHANGED / BROKEN
    changed_by_event_id: int | None
    # ── 非对称 ──
    is_mutual: bool               # A→B 与 B→A 是否同一关系
```

**双向记录**：`is_mutual=False` 时，A→B 与 B→A 是**两条独立记录**。这直接支撑：
- 「A 信任 B，但 B 在利用 A」这类张力（旧模型无法表达）
- 关系演化有明确的事件归因（`changed_by_event_id`）

### 关系网络的健康度指标

| 指标 | 定义 | 目标 |
|---|---|---|
| `tension_ratio` | 有 `true_facing != surface_facing` 的关系占比 | 15%~40%（太低=没有暗线，太高=人人两面） |
| `non_mutual_ratio` | 非对称关系占比 | ≥ 10% |
| `relation_evolution_rate` | 每 50 章发生变化的关系数 | ≥ 3 |
| `protagonist_relation_count` | 主角的有效社会关系数 | ≥ 8 且随卷增长 |
| `relation_kind_entropy` | 关系类型分布熵 | 越高越好（防全是"同门"） |

## 对策 ④ 健康状态机 + 细纲强制恢复节拍（解决痛点 1）

### 实测问题（完整根因链）

**根因 1：恢复靠 prompt 催促，不靠规划**

恢复机制的全部实现是（`app/memory.py` `_fmt_impacts` L1001-1006）：
```python
if el >= th:       warn = " ⚠️已超恢复期，本轮必须推进（恢复剧情或明示永久化）"
elif el >= th*0.8: warn = " ⚠️接近恢复期，建议本轮推进"
```
阈值表（`_IMPACT_BASE_TH`）：
```python
("伤势","轻微"):1 ("伤势","轻"):1 ("伤势","中"):2 ("伤势","重"):3 ("伤势","极重"):5
("后遗症","轻微"):3 ... ("后遗症","极重"):12
("心魔",...):3~12    ("代价",""):12    ("诅咒",""):999
```
修正因子：核心角色 ×1.2；有治疗资源 ×0.7；无资源 ×1.3；卷末 20% ×0.6。

**根因 2：抽取器规则与生成机制死锁**

`app/agents/post_processor.py` L42 明文：
```
· 好转/痊愈/解除/缓解必须能在 events 找到该角色的治疗/恢复/解咒/补偿事件，
  否则不得报恢复类状态；
```
→ 抽取器**不允许**无治疗事件就报恢复
→ 但**没有任何机制**去生成治疗事件
→ 伤势永久停留「维持」
→ 同时每章被标注「本轮必须推进」
→ Writer 看到"必须推进"却无场景支持 → 一笔带过或忽略
→ Editor 判「未推进」→ 低分

项目自己的记录（`docs/TODO_20260913.md` §7.1）：
```
1-9  5/10 「多项硬性违规：楚渊多项标注『本轮必须推进』的损伤
           （左肩剑创、后腰擦伤、内腑…）未推进」
1-10 4/10 「严重AI味…及关键设定矛盾（人物状态表多项标注『本轮必须推进』的伤势…）」
```

**根因 3：severity 枚举三方不一致**

| 位置 | 档位 |
|---|---|
| `memory.py` 阈值表 | 轻微 / 轻 / 中 / 重 / 极重（**5 档**） |
| `post_processor.py` prompt | 轻 / 重 / 极重（**3 档**） |
| fallback | "重" |

→ 「轻微」「中」永远不会被产生，而这两档（1 章、2 章）正是最快催恢复的

**根因 4：章号双表示导致灾难 bug**

`memory.py` `_impact_since_global` docstring 记录的实测事故：
```
书 24 实测 P0：since_ch 被写入侧存成卷内号，消费侧 ctx["cur_ch"] 是全局号
→ 已持续 = 10012 - 1 = 10011。
阈值仅 1~3，于是每章恒真 → 每个损伤每章都挂「本轮必须推进」，
一章推进不完 7 处 → Editor 每章判「必推进的损伤未推进」→ 4~5 分 + 必改失败。
```

### 架构对策

#### 4.1 损伤是一等状态，有明确生命周期

```python
class InjurySeverity(str, Enum):
    MINOR = "轻微"; LIGHT = "轻"; MODERATE = "中"; SEVERE = "重"; CRITICAL = "极重"

class InjuryStatus(str, Enum):
    NEW = "新发"; WORSENED = "恶化"; STABLE = "维持"
    IMPROVING = "好转"; RELIEVED = "缓解"
    HEALED = "痊愈"; REMOVED = "解除"
    PERMANENT_MITIGABLE = "永久·可缓解"; BOUND = "绑定"

class Injury(BaseModel):
    id: int
    entity_id: int                    # 谁受伤（引用 Entity.id）
    kind: InjuryKind                  # 伤势/后遗症/心魔/代价/诅咒
    name: str
    severity: InjurySeverity
    status: InjuryStatus
    since_chapter: int                # ★ 单一章号（O-04）
    expected_heal_chapter: int | None # ★ 规划出来的恢复章（见 4.2）
    heal_condition: str | None        # 恢复所需条件（"需疏络散持续治疗"）
    heal_scene_planned: bool          # ★ 细纲里是否已排入恢复场景
    is_permanent: bool
    updated_chapter: int
```

**关键新增字段**：
- `expected_heal_chapter` —— 恢复**被规划**，不是被催促
- `heal_scene_planned` —— 布尔闸门：未排入场景的伤势，不允许进入"催恢复"状态
- 枚举**单一来源**（Pydantic），prompt 由 schema 生成 → 消除三方不一致

#### 4.2 恢复必须走细纲（这是解决「太突然」的关键）

#### 4.2.0 先看旧项目的**能力矩阵**（这是根因的最终形态）

| 角色 | 能看到损伤 | 能规划治疗 | 能落实治疗 |
|---|---|---|---|
| `architect`（细纲规划） | ❌ **无损伤字段、无账本快照** | ❌ | — |
| `writer`（正文） | ✅ 有损伤区 | ❌ 受细纲硬约束 | ⚠️ 只能照细纲写 |
| `post_processor`（记录） | ✅ | ❌ | ❌ |
| `editor`（审校） | ✅ | ❌ | ⚠️ 只能打回重写 |

> **没有任何一个 agent 同时具备「看到损伤」和「规划本章节拍」两个能力。**

**证据链**：
1. 唯一催促（`memory.py:1001-1006`）只到 writer：`_fmt_impacts → _fmt_char_line → build_context → context["states"] → writer prompt`
2. writer 面对两条矛盾硬指令：损伤区说「本轮必须推进」、细纲区说「最高优先级、禁止新增细纲之外的重要转折」→ **实测 writer 服从细纲**（这是正确的服从）
3. 细纲三处独立确认不含伤势：`architect.py:1806-1808`（prompt 定义 entry/exit state 四项为「地点·时间·在场人物·谁知道什么」）、`outline_lint.py:121-125`（校验文本同上）、`detail_review.py:809`（审校准则同上）
4. `VALID_BEATS`（`schemas.py:25`）**没有 `heal`/`recovery`** —— 恢复不是合法节拍类型
5. `editor.py:69` 把「规划失败」的成本转嫁为「审校惩罚」→ 死循环，每章扣分

**结论**：修复不需要改状态机合并逻辑，需要**让细纲规划者拿到损伤账本，并把「恢复」变成可规划的一等节拍**。

#### 4.2.1 恢复流程（新设计）

**流程**：
```
1. 抽取器报「新发/恶化」伤势
   → HealthScheduler 计算 expected_heal_chapter（用阈值表 + 修正因子）
   
2. 规划细纲时，若某章 chapter_no == expected_heal_chapter
   → ChapterPlan.health_beats 必须包含一条恢复节拍：
     HealthBeat(injury_id, action=HEAL, scene_ref=<本卷某个 SceneBeat>)
   → 该 SceneBeat 的 goal/obstacle/outcome 必须与"治疗"相关
   → 校验：恢复节拍必须占用一个真实场景，不能是"顺手一句带过"
   
3. Writer 收到细纲 → 恢复有场景支撑 → 自然写出
   
4. 抽取器报「痊愈」→ 有 events 支撑 → 通过
```

**三条硬约束（针对旧项目的三个缺陷）**：

| 旧项目缺陷 | 新设计约束 |
|---|---|
| `architect` 看不到损伤 | `detail_planner` 的输入**必须**包含活跃伤势列表 + `HealthScheduler` 排好的节拍 |
| `VALID_BEATS` 无 heal | `BeatType` **必须**新增 `HEAL` / `RECOVERY_PREP`，且是合法节拍 |
| writer 面对矛盾指令 | 伤势推进指令**只经细纲下达**，不再独立注入 writer（消除指令冲突） |

**这同时解决「太突然」和「一直不恢复」**：
- 有 `expected_heal_chapter` → 恢复有预期，不是随机
- 恢复占用真实场景（≥1 个 SceneBeat）→ 有铺垫，不突然
- 有闸门强制排入 → 不会永远停留「维持」

#### 4.2.2 拆掉「记录一致性 → 叙事义务」的自锁

旧项目的守卫（`memory.py:2114-2121`）要求：**同一个 LLM 在同一次输出的 `events` 字段里**同时含角色名 + 治疗语义词，才允许报恢复。

**自锁**：prompt 要求 `events` 只写「2~5 条关键事件」→ 过渡章可能没有 events → 恢复申报被拒。

**新设计**：恢复的证据来自**结构化的 `HealthBeat` 记录**，不来自自由文本 `events` 的关键词匹配：

```python
# 旧：字符串关键词双重合取（脆弱、自锁）
if name in events_blob and any(k in events_blob for k in KWS): allow_recovery()

# 新：结构化证据链（精确、无自锁）
if injury.heal_scene_planned and chapter_plan.has_health_beat(injury.id, action=HEALED):
    allow_recovery()
```
好处：
- 不再要求 `events` 承担它 schema 上没承诺的职责
- 判定是**确定性的**（可查证 `health_beats` 表），不依赖关键词匹配
- 「押进城/走进大殿」这类无关事件不会再被误当痊愈依据（旧 bug）

#### 4.2.3 修掉三个次要放大器

| 放大器（旧项目） | 新设计 |
|---|---|
| `only_changes=True` 过滤掉配角的「维持」伤势 → **连催促都不出现** | 配角伤势进入调度器，只是预热序列更短；**不得整条跳过** |
| `equip` 参数传递不一致 → 配角永远按「无治疗资源」算（阈值 ×1.3） | 治疗资源判定**单一入口**，参数由调度器显式传入，不依赖调用方记得传 |
| `("诅咒",""): 999` → 永不催促，且无代码把解咒伏笔与诅咒关联 | 诅咒由**伏笔系统**驱动：诅咒类伤势必须绑定一个 `resolve_foreshadowing`，由伏笔回收排程驱动 |

#### 4.2.4 阈值反向引导的教训（枚举多源）

旧项目实测事故（`memory.py:291-294` 注释自述）：
```
原表只登记「轻/重」两档，而模型实际会写「中」「极重」「轻微」
→ _impact_threshold 拿不到 base → 返回 None → 这些损伤永远不会被催
实测书 24：最重的「神魂受创（伤势·极重）」恰恰是唯一不催的那条，
而轻伤催得最凶 —— 注意力被反向引导。
```

**新设计硬约束**：阈值表的 key **必须**由 `InjurySeverity` 枚举生成（穷尽性由类型系统保证），不允许手写字典漏项。配单元测试：遍历 `InjurySeverity × InjuryKind` 全组合，断言每个组合都有阈值。

**这同时解决「太突然」和「一直不恢复」**：
- 有 `expected_heal_chapter` → 恢复有预期，不是随机
- 恢复占用真实场景（≥1 个 SceneBeat）→ 有铺垫，不突然
- 有闸门强制排入 → 不会永远停留「维持」

#### 4.3 伤势"预热"机制（解决突然性）

恢复不能只在恢复章出现。`HealthScheduler` 在 `expected_heal_chapter` 之前的 **N 章**（默认 3~5，按伤势严重度）自动注入**铺垫节拍**：

```python
class HealthBeat(BaseModel):
    injury_id: int
    action: HealthAction   # SEEK_TREATMENT / ACQUIRE_MEDICINE / CONDITION_WORSENS
                           # / TREATMENT_ATTEMPT / RECOVERING / HEALED
    chapter_no: int
    scene_ref: int         # 必须指向本卷某个真实 SceneBeat
    note: str
```

典型预热序列：
```
ch 10  新发      左肩剑创（重）
ch 12  SEEK_TREATMENT   寻医（场景：找到镇上郎中）
ch 14  ACQUIRE_MEDICINE 获取药引（场景：冒险采药）
ch 18  TREATMENT_ATTEMPT 服药（场景：疗伤过程，可被打断）
ch 21  RECOVERING       好转
ch 24  HEALED           痊愈
```
**每一步都有场景** → 恢复是剧情的自然结果，不是系统给的判罚。

#### 4.4 结构性防呆

| 防呆 | 内容 |
|---|---|
| 单一章号 | 全书单调递增 int（O-04）；显示层负责格式化成「卷-章」 |
| 枚举单一来源 | Pydantic Enum → 生成的 prompt 约束 → 抽取器只能输出合法值 |
| 无场景不催促 | `heal_scene_planned=False` 的伤势**不注入**"必须推进"警告（消除死锁） |
| 恢复需场景 | 报「痊愈」必须能在 `health_beats` 找到对应 `HEALED` 记录且其 `scene_ref` 真实存在 |

### 验证指标

| 指标 | 旧项目实测 | 目标 |
|---|---|---|
| 伤势平均存续章数 | 长期停留「维持」 | 接近 `expected_heal_chapter - since_chapter` |
| 恢复是否有铺垫 | 无机制 | 100% 的 `HEALED` 有前序 `HealthBeat` |
| 因伤势未推进导致的 Editor 低分 | 高频（§7.1 实证） | 0 |

## 对策 ⑤ 可阻断的文风门禁 + 质量打分卡

### 实测问题

`backend/prose_style_config.json`（生产实时值）：
```json
{ "enabled": true, "shadow": true,      ← 只观测，不阻断
  "dialogue_floor": 0.12,               ← 对话占比 12% 即合格
  "duplicate_threshold": 0.72, "ngram": 4, "cross_window": 5 }
```

### 关键约束：注水不可确定性测量（这是负结果，必须尊重）

旧项目 `app/prose_style.py` docstring 记录了**四次独立验证的失败**：

| 尝试 | 方法 | 结果 |
|---|---|---|
| 1 | 段落级 Dice（字面复制） | 全 47 章最高 **0.519**；`>=0.60` 章数 **0/47** |
| 2 | 句子级重复 | 第 13 章 177 句仅 1 种重复句；第 2、31 章为 **0** |
| 3 | 「无新增内容单元」段落占比 | 实测 p50 = **0.0%** —— 一本被评为「非常注水」的书得到「零注水」。**已废弃该指标** |
| 4 | 低阈值段级相似度探针 | threshold 0.30 → 12 对/9 章；0.50 → **0 对**。合成对照（两段不同措辞写同一拍）在 0.30 下**命中 0** |

**根本原因**：同一拍会**换一批词**来写；且注水段落**一直在引入新道具与编号**，所以「有无新专名」也抓不到。

**结论（写入架构约束）**：
> **不得为「无推进重复（注水）」建确定性闸门** —— 那会是一台假阴性机器。
> 该问题只能靠 LLM 语义审校 + 人工盲读。

### 架构对策：打分卡只做「触发器」，LLM 做「判断器」

#### 5.1 确定性打分卡（零 LLM、可复现、毫秒级）

继承旧项目已验证有效的字面指标，**并重新标定阈值**：

```python
class DeterministicScorecard(BaseModel):
    chapter_no: int
    # ── 字面层（旧项目已验证有效，口径继承）──
    cross_chapter_overlap: float | None   # 与近 5 章 4-gram 重叠（旧基线 p50 9.85%）
    intra_redundancy: float | None        # 章内 4-gram 冗余（旧基线 p50 6.21%）
    dialogue_ratio: float | None          # 对话占比
    top_repeated_ngrams: list[str]        # 章内高频 n-gram
    triple_parallelism: int               # 三段式排比数（旧基线 60 处/33 章）
    ending_pattern: EndingPattern         # mid_action/omen/dialogue/summary/time_skip/other
    cliche_hits: list[str]                # 套话命中（旧项目有 CLICHES 表）
    metaphor_density: float               # 比喻密度（新增）
    sentence_len_cv: float                # 句长变异系数
    # ── 结构层（新增，来自对策 1/2/4）──
    outline_adherence: float              # 细纲场景落实率（机械比对）
    hook_landed: bool                     # 章末是否落在规划钩子上
    state_consistency: StateConsistency   # 伤势/装备/位置/关系一致性
    unsupported_entities: list[str]       # 无引入依据的新名词
    # ── 汇总 ──
    score: float                          # 加权总分
    triggers: list[TriggerReason]         # 触发了哪些重审理由
```

**口径继承原则**：`prose_style.py` 的指标口径是**用书 23 的 47 章 baseline 反解并对齐**过的（例如 4-gram 必须在「去空白但**保留标点**」的文本上切分，否则章内冗余率会从 6.2% 掉到 4.2%，与 baseline 不符）。这些口径要**照抄**，避免重新校准。

**关于 `None`**：旧项目设计「缺省即不通过」—— 无法评估时返回 `None`，**绝不返回 0**。这个约定要继承。

#### 5.2 触发规则（阈值 → LLM 审校）

```python
# 无条件 LLM 审（黄金三章 + 结构关键章）
ALWAYS_REVIEW = {1, 2, 3} | {卷末章} | {beat_type in (CLIMAX, BOSS)}

# 阈值触发（任一命中 → LLM 审校 + 定向重写）
TRIGGERS = {
    "cross_chapter_overlap > 0.15":    "与近 5 章重复度过高（旧基线 p50 9.85%，max 14.5%）",
    "dialogue_ratio < 0.25":           "对话占比过低（旧下限 0.12 过松，需重新标定）",
    "cliche_hits >= 5":                "套话密集",
    "metaphor_density > threshold":     "比喻过量",
    "outline_adherence < 0.8":          "细纲场景未落实",
    "not hook_landed":                  "章末未落在规划钩子",
    "state_consistency.has_violation":  "状态矛盾（伤势/装备/位置）",
    "unsupported_entities":             "存在无依据新名词",
    "score < threshold":                "总分不达标",
}
```

#### 5.3 LLM 审校的职责边界（重要）

旧项目实测 Editor **反复给出空 `issues` / 空 `revised_content`** 导致重写空转（`no_revised_content`、`too_short:3839<4600`、`no_improve:6->6`）。

**新设计**：LLM 审校**必须输出结构化结果**，且被强制：
```python
class ReviewResult(BaseModel):
    issues: list[ReviewIssue]          # 每条含 severity / 位置 / 说明
    # 若 issues 非空，revised_content 必填（schema 层强制）
    revised_content: str | None
    score: float
    # 不允许「notes 里说了问题但 issues 为空」
```
**关键约束**：`review_json.actions_taken` 必须由**代码**根据 `revised_content` 是否存在生成，不得采信模型自述。旧项目实测过模型在 `notes` 声称"已改写"而 `revised_content=null`（`AGENTS.md` 记录）。

| 对话占比 p50 | 10.6% | > 25% |
| 文风门禁是否阻断 | `shadow: true`（不阻断） | 阈值命中即阻断 |
| LLM 审校产出可用修订稿率 | 空转（`no_revised_content`） | ≥ 80% |

## 对策 ⑥ Agent 拆分 + Prompt 单一来源

### 实测问题

- `post_processor.ChapterPostProcessor.system` 单条 **>10,000 字符**，一次要求提取 **11 类**信息（cards / summary / state_updates / deaths / relationship_updates / events / plot_progress / claims / schema_delta / hang / entities）
- 全仓三引号 prompt 文本合计 **172,822 字符**

#### 6.1 按「职责独立、失败可隔离」拆分 Agent

| 新 Agent | 职责 | 输入 | 输出 | 模型档位 |
|---|---|---|---|---|
| `BibleArchitect` | 世界观圣经 | brief | `Bible` | 高 |

| `ChapterWriter` | 正文 | 组装后的 context | `str` | 高 |
| `SceneExtractor` | 事件/状态抽取 | prose | `ExtractedState` | 中 |

| `RelationExtractor` | 社会关系抽取（**只抽关系**） | prose + 既有关系 | `RelationDelta[]` | 中 |

### 实测问题

```python
prompt_tokens      = 9,151,550
cached_tokens      = 4,023,724   → 命中 44.0%
completion_tokens  = 8,970,128
reasoning_tokens   = 6,876,206   → 占 completion 76.7%
blank (空输出)      = 223 / 1003 = 22.2%
```

按 agent：
```
memory           平均输入 32,220 字符（最大），缓存命中 10.9%（最低）★
verifier         空输出 62.3%，reasoning/completion 99.4%

```

按模型（同一套 prompt）：
```

deepseek-v4.1    空输出 25.9%   缓存 43.1%
qwen3.8-flash    空输出 91.4%   缓存 12.3%
```

### 架构对策

#### 7.1 观测契约（一期必须先补的基础设施）

```python
class LLMCallRecord(BaseModel):
    # ── 标识 ──
    call_id: str; trace_id: str; node_name: str; attempt_no: int
    model: str; provider: str
    # ── 用量（继承旧项目正确契约）──
    prompt_tokens: int | None         # 缺失保持 None，不冒充 0
    completion_tokens: int | None
    reasoning_tokens: int | None
    cached_tokens: int | None         # ★ 缓存命中
    cache_creation_tokens: int | None
    total_tokens: int | None
    usage_source: UsageSource         # NATIVE | PARTIAL | UNAVAILABLE
    usage_complete: bool
    # ── ★ 旧项目完全缺失的诊断字段 ──
    finish_reason: str | None         # stop / length / content_filter / tool_calls
    # ── 上下文归因（旧项目的北极星指标要求，但未落实）──
    context_breakdown: dict[str, int] # {bible: N, outline: N, states: N, rag: N, ...}
    # ── 缓存分析 ──
    prompt_prefix_hash: str           # 稳定前缀 hash（用于分析缓存命中/未命中）
    prompt_total_chars: int
    # ── 性能 ──
    elapsed_ms: float; started_at: datetime; finished_at: datetime
    status: CallStatus                # OK | BLANK | FAILED | TIMEOUT
    retry_reason: str | None
```

**四个必补字段**：
1. **`finish_reason`** —— 旧项目 100% 缺失。没有它就无法区分"模型主动停"与"被 max_tokens 截断"，**这是诊断 22.2% 空输出的前提**
2. **`context_breakdown`** —— 逐来源拆分输入 token。旧项目 `AGENTS.md` 把它列为北极星指标但从未落实
3. **`prompt_prefix_hash`** —— 分析缓存命中/未命中的依据
4. **`cache_creation_tokens`** —— 区分"读缓存"与"写缓存"

#### 7.2 缓存友好分层（核心机制）

**实测证据**：`memory` agent 输入最大（32K 字符）但缓存命中最低（10.9%）。原因：它的 prompt 是「本章正文 + 账本快照」，**正文每章变化且拼在前面**，破坏了前缀。

旧项目 `writer._build_prompt` 的注入顺序（L411-565）显示：稳定内容（圣经）在前，但**易变内容（时间线/状态表/前文/伏笔）与稳定内容交错混排**，且 system prompt 里 `.format()` 注入了每章变化的字数参数。

**新规范（强制）**：
```
Prompt 结构 = [稳定前缀] + [准稳定层] + [易变层]

① 稳定前缀（全书不变，放最前）
   - 角色定义（"你是资深网文作家…"）
   - 输出格式约束
   - 世界观圣经（全书定稿后不变）
   → 目标：这部分 100% 命中缓存

② 准稳定层（按卷/按段变化）
   - 本卷升级台阶、卷目标
   - 本段段落目标
   - 文风规则（固定文本，不注入动态参数）
   → 目标：段内 100% 命中

③ 易变层（每章变化，放最后）
   - 前情时间线、上一章结尾、人物状态表、RAG 片段
   - 本章细纲、钩子、前后锚点
   → 无法缓存，但要尽量短
```

**配套硬约束**：
| 约束 | 理由 |
|---|---|
| 字数参数**不得**注入 system prompt | 旧项目 `.format(MIN_CHARS=...)` 让 system 逐章变化，破坏缓存 → 改为放在易变层尾部 |
| 时间戳/随机数/序号**不得**出现在稳定前缀 | 破坏缓存 |
| 稳定前缀**逐字节稳定** | CI 检查：同书相邻章的 stable prefix hash 必须相同 |
| 缓存命中率纳入 CI | 低于目标即失败 |

#### 7.3.0 ⚠️ 优先级更正：缓存命中不是第一优先（重要）

**用户痛点 7 的表述是「token 预算分析优化缓存命中功能」**。但实测成本结构显示，
**缓存命中不是最大的口子**。按 MiMo Token Plan 权重（hit=2 / miss=100 / output=200）：

| token 类型 | token 数 | Credits | 占比 |
|---|---:|---:|---:|
| hit（命中输入） | 4,023,724 | 8,047,448 | **0.35%** |
| miss（未命中输入） | 5,127,826 | 512,782,600 | **22.15%** |
| output（输出，**含 reasoning**） | 8,970,128 | 1,794,025,600 | **77.50%** |

**反事实测算**：
```
reasoning 降到 0     → Credits 2.315G → 0.940G，省 59.4%
cache hit 44% → 80%  → Credits 2.315G → 1.992G，省 13.96%
```

**独立验证（本次核算，按不同 output 单价做敏感性分析）**：

| output 单价假设 | hit 占比 | miss 占比 | output 占比 | hit→80% 省 | reasoning 减半省 |
|---|---|---|---|---|---|
| $0.9/M | 0.25% | 15.97% | **83.78%** | 10.06% | **32.11%** |
| $1.2/M | 0.20% | 12.48% | **87.32%** | 7.86% | **33.47%** |
| $0.3/M（对缓存最有利） | 0.57% | 36.17% | **63.27%** | 22.79% | **24.25%** |

> **结论：即使在对缓存最有利的假设下，缓存命中仍只占成本 0.57%，而 output 占 63%。**
> **正确的优先级是：先治 output（含 reasoning），再治缓存命中。**
> 缓存命中仍要做（省 8%~23% 不是小数目），但**不是第一优先**，且必须知道它的天花板。

**按 agent 的 Credits 份额（生产实测）**：

| agent | Credits 份额 |
|---|---|
| **architect** | **42.0%** |
| editor | 20.3% |
| memory | 14.7% |
| writer | 13.6% |
| verifier | 6.4% |
| 其余 4 个 | 3.0% |

> ⚠️ **不要用离线 benchmark 的成本排名做决策**：离线 artifact 显示 `editor 59.3%` 排第一，
> 而生产实测是 **`architect 42.1%`** 排第一 —— 因为离线套件严重欠采样 architect
> （生产 401 条 architect trace vs 离线只测了 26 条 attempt）。
> **`architect` 的 hit 率其实最高（60.3%），但它的 output 有 75.2% 是 reasoning、绝对量大（2.55M prompt / 4.34M completion），所以即使命中率高，它仍是第一成本项** —— 再次印证「输出侧才是主战场」。

#### 7.3.1 ⚠️ 但「砍 reasoning 长度」已被证伪（避免走弯路）

直觉上「reasoning 占 59.4% 成本 → 那就限制 reasoning 长度」。**这条路已被实测堵死**。

`backend/test_reasoning_caps.py:5-16` 用 **74 条真实 attempt** 验证配置的 reasoning 上限：

```
editor   实测峰值 3853   vs 配置上限 5000    → 从未撞到
verifier 实测峰值 3082   vs 配置上限 0(不限)  → 不适用
memory   实测峰值 8004   → 唯一接近的一次
```

该文件自述结论：**「上限不是成本杠杆…收益 ≈ 0」**。

> **reasoning 占比高，但它是模型自发产生的，靠 `reasoning_max_tokens` 这个旋钮拧不动。**

**真正的 reasoning 成本杠杆只有三个（按可行性排序）**：

| # | 杠杆 | 说明 |
|---|---|---|
| 1 | **换模型 / 换档位** | reasoning 量是**模型属性**。`verifier`(99.4%) / `base`(98.4%) / `editor`(81.7%) 这些近乎「全思考零正文」的角色，应路由到**默认不思考的模型**，而非限制思考长度 |
| 2 | **减少调用次数** | `verifier` 6.4% + `memory` 14.7% 的 Credits 主要来自「调用多」而非「单次贵」。`memory` 的 hit 率只有 **10.9%**（最低），是重复 prompt 的重灾区 |
| 3 | **消灭 blank 空转** | **223 次 blank = 14.36% 的 token 纯浪费**，这是**唯一确定可回收**的一块 |

#### 7.3.2 blank 空转：14.36% 的纯浪费（确定性可回收）

| 指标 | 值 |
|---|---|
| attempt 状态分布 | `ok 772` / **`blank 223`** / `failed 8` |
| **blank 浪费 token** | **2,602,167 = 全部 token 的 14.36%** |
| blank 按模型 | `deepseek-v4.1-flash` **2,313,604**（159 次）/ `deepseek-flash` 160,888(10) / `qwen3.8-flash` 127,675(53) |

> **223 次「有请求、有 token 消耗、零有效产出」= 22% 的调用是空转。**
> 且 `problems.jsonl` 里 `思考 token 已计费` / `micro_output` **零命中** ——
> 说明 `_MICRO_OUTPUT_DISCARDS` 的观测埋点在**生产里从未触发过**，
> 真正烧钱的是 `blank` 这条**更宽**的路径（旧项目的埋点打偏了）。

#### 7.3.4 成本口径的四个一致性缺陷（必须在重写时修）

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | **reasoning 被重复计入** | `reasoning ⊆ completion`（**896/897 行**验证 `prompt+completion == total`），但 `trace_service.py:117-120` 算 `completion + reasoning`，`:129-132` 还算 `prompt+completion+reasoning` → **任何基于这两处的成本函数会多收 77% 的输出费** |
| 2 | **两份互相矛盾的 Credits 公式** | `cache_attribution.py:65-74`（NULL-safe、含折扣）vs `editor_patch_ab.py:199-204`：后者用 `usage.get(k) or 0`（`:201-203`）**把 NULL 变 0 → 把整段 prompt 当 miss 计费**。`test_editor_patch_ab.py:30-32` 还把这个行为**钉成正确** |
| 3 | **成本是 model-blind 的** | 只有一套 MiMo 权重，却用在 `deepseek-v4.1-flash`（**占生产 61% 的 attempt**）和 `qwen3.8-flash` 上（不同 provider、不同价） |
| 4 | **`native` 是弱保证** | `native` 只要 ≥3/5 字段（`observability.py:118`）→ 33 行 `native` 的 `cached_tokens` 为 NULL → `credits_for` 会**既不收 hit 也不收 miss**，**漏报**而非多报 |

**新设计要求**：成本函数必须基于**单一事实来源**（`prompt_tokens` / `cached_tokens` / `completion_tokens`，
其中 **`reasoning_tokens ⊆ completion_tokens`，不得相加**），且**按模型单价配置化**（不得 model-blind）。

#### 7.3.6 缓存命中的真实天花板与正确的做法

**缓存杀手定位**：`memory.py:1624-1629` 的 `bible_inject.select` ——
`_bible_query = f"{plot} {title}"` **逐章不同** → **全书最稳的圣经前缀在第一个块就分叉**。

**每章输入的稳定比例实测**：

| 上下文块 | 跨章稳定性 | 可缓存 |
|---|---|---|
| `bible`（裁剪后） | 全书稳定（**但被按章裁剪破坏**） | ✅ 若能去掉按章裁剪 |
| `genre_state` + `genre_blocks` | 类型级稳定 | ✅ |
| `entity_registry` | 单调增长 | ✅（前缀部分） |
| system prompt | 完全稳定 | ✅（**当前根本没计**） |
| `states` + `timeline` | 滑动/渐变 | ⚠️ 部分 |
| `prev_prose` + `rag_snippets` + `style_snippets` | 逐章全新 | ❌ |
| `hang` / `bridge` / 伏笔 / 复习 | 逐章全新 | ❌ |

**估算**：逐章可变块合计约 **55%~70%**；真正跨章稳定的是 `bible + genre + entity_registry`，约 **30%~45%**。

> **这就是为什么 hit 率卡在 33%~44%**：稳定段的**长度上限大约就是 40%**，
> 而现有实现连这 40% 都没拿到全部（章级只有 **32.9%**）。

**要达到 80% hit 需要做的（按收益排序）**：
1. **去掉 bible 的按章裁剪**（或改成「全量圣经进缓存前缀 + 按章选取的部分放到尾部」）—— **单点最大破坏**
2. **`entity_registry` / `genre_*` 移到 prompt 最前**，与 bible 合并成一个「全书不变前缀块」
3. **`prev_prose` / `rag` / `style` / `hang` / `bridge` 全部移到 prompt 末尾**，确保**无一块稳定内容夹在它们中间**
4. **修 `system_instruction: 0`**，让 system prompt 参与前缀
5. provider 支持时对前缀块打 `cache_control: {type: "ephemeral"}`
6. 收敛 `bible_inject.select`，或改为「不改内容只改顺序」
7. **续推轮次（4 条 messages）与首次（2 条）前缀不同** → 考虑对续推单独维护缓存键

**一个反直觉的正面发现**（focused artifact，verifier）：`first=0.934` / `retry=0.985`
→ **重试的缓存命中反而更高**（prompt 完全相同，provider 已缓存）。

#### 7.3.8 核心机制设计（原 §7.3 内容，现置于正确优先级下）

**实测问题**：`reasoning_tokens` 占 completion **76.7%**（verifier 达 99.4%）。旧项目机制（`client.py`）：
```python
max_tokens = max(4096, reasoning * 4)   # 思考与输出共用上限
# 可用输出预算 = 4x - x = 3x
```
以及「微产出判废」：思考烧 3000+ 字却只吐 <20 字 → 判废重试 → **这是空输出的直接机制之一**。

**同一套策略在不同模型上结果差异极大**（mimo 0% vs qwen 91.4%），说明策略不具鲁棒性。

**新规范**：
```python
class ModelCapability(BaseModel):
    supports_reasoning: bool
    reasoning_control: ReasoningControl | None   # NONE | EFFORT | BUDGET | TOKEN_LIMIT
    max_output_tokens: int
    context_window: int
    supports_structured_output: bool
    cache_mode: CacheMode                        # NONE | AUTOMATIC_PREFIX | EXPLICIT_CONTROL
    concurrency: int
```

**按节点类型分配策略**：

| 节点类型 | 思考策略 | 理由 |
|---|---|---|
| `ChapterWriter` | 允许思考，但**输出预算下限保障** | 正文是最终产物，不能因思考被挤掉 |
| `DetailPlanner` / `SkeletonPlanner` | 允许思考，结构化输出 | 规划需要推理 |
| `ScorecardEngine` / `HealthScheduler` | **零 LLM** | 确定性 |
| `SceneExtractor` / `EntityResolver` | **关闭或最小化思考** | 抽取是模式匹配任务，不需要长思考；旧项目 `entity_classify` 100% 空输出正是反例 |
| `StyleCritic` | 中等思考 | 需要语义判断 |

**硬约束**：节点声明**所需能力**，路由器按能力匹配模型；**不得**在代码里写 `if model == 'xxx'`。

#### 7.4 空输出治理

```
1. 采集 finish_reason（诊断前提）
2. 空输出率纳入 SLO，按节点监控
3. 空输出率超阈值的 node×model 组合自动降级到备用模型
4. 「微产出判废」改为「按模型能力自适应」：reasoning 型模型给足输出预算，
   非 reasoning 型不做 4x 放大
```
