## 1. 已识别的风险

### R-01 · LangGraph 版本 API 变动（中）

| 项 | 内容 |
|---|---|
| 风险 | LangGraph 仍在大版本演进，patch 级也有破坏性变更 |
| 实测证据 | 官方 release policy 承诺「breaking 只在大版本」，但**有 3 个 patch 级破坏的一手反例**：`langchain 1.0.6`、`langgraph-prebuilt 1.0.2`、`checkpoint-postgres 2.0.22` |
| 触发条件 | 升级 patch 版本 |
| 缓解 | ① **锁定精确版本**（不用 `^` / `~`）；② 业务逻辑零框架依赖（验收标准：`grep -r "langgraph" src/storyforge/domain/` 返回空）；③ 升级前跑全量回归；④ ⚠️ **绝对不要 pin `langgraph` 1.0.x / 1.1.x** —— 它们对 `langchain-core` **无上界约束**，且 1.0.x 声明 `langgraph-checkpoint<3.0.0`，与 checkpoint 4.x **互斥** |
| 版本基线（2026-09 实测） | `langgraph 1.2.11`（2026-08-11）/ `langchain-core 1.6.3` / `langchain 1.4.0` / `langgraph-checkpoint 4.2.0` / `-sqlite 3.1.1` / `langgraph-sdk 0.4.4` / `langsmith 0.12.4` |
| 依赖自洽性 | 已验证：`langchain 1.4.0` → `langgraph>=1.2.11,<1.3.0` → `langchain-core>=1.4.7,<2` |
| 不引入 | `langchain-classic` / `langchain-community` / **`langgraph-supervisor`（已停止维护）** |

### R-02 · LangGraph checkpoint 存储膨胀（中高）

| 项 | 内容 |
|---|---|
| 风险 | checkpoint 默认保存全部 state 历史，序列化体积随轮次增长 |
| 实测证据 | LangChain 官方博客承认 200 轮编码 agent 序列化 **5.3 GB**；社区实测 32 线程 **1.24 GB**（40 KB 静态文本被重序列化 3,200+ 次） |
| 触发条件 | 长跑（1,500 章）+ 大 State |
| 缓解 | ① **State 只放引用不放正文**（`01-总体架构` §3.4）—— 这是**最高优先级缓解**，且该措施在 LangGraph / Temporal / DBOS 上**完全同构**（做完后换引擎成本从"重写"降为"换 adapter"）；② 定期清理旧 checkpoint；③ 监控 checkpoint DB 体积 |
| 备注 | 与旧项目旧问题**同构**：旧项目把 400 章 `outline` 塞进 `books.outline` 单列。**必须避免重演**。 |

### R-03 · checkpointer ≠ 持久执行（中高）

| 项 | 内容 |
|---|---|
| 风险 | checkpoint 保存**数据**，不保存**执行**。进程死亡后需**自己检测失败并重新入图** |
| 实测证据 | LangChain 自身 durability 语义 + Temporal 官方文档共同印证 |
| 缓解 | ① 实现显式「恢复入口」（检测未完成运行 → 重新入图）；② 一期即测试 `kill → resume`（P5 验收项）；③ 不把「自动恢复」当默认（旧项目刻意不自动续跑以防重启即烧 token，**这个判断是对的**） |

### R-03b · 节点必须幂等（★ 新发现，高）

| 项 | 内容 |
|---|---|
| 风险 | LangGraph 会**静默重放**超时节点 → 重复烧 token |
| 实测证据 | `langgraph#7417`（**53 条评论仍 open**）：**>180s 的调用在 LangGraph Cloud 被静默重放**，造成 2~3× 冗余成本 |
| 为什么对本项目特别危险 | **章节生成极易超过 180s** —— 旧项目实测 `editor` 平均 **117s**、`architect` **72s**、`memory` **61s**，且 writer 流式生成长文本必然更久 |
| 缓解 | ① **每个 LLM 节点必须幂等**：以 `(book_id, chapter_no, node_name, attempt_no)` 为幂等键，重放时**复用已有结果**而不重新调用；② 调用前先查 `llm_calls` 是否已有该键的成功记录；③ 单节点超时阈值要显式设计（不依赖框架默认） |

### R-03c · 沉默数据损坏（★ 新发现，中高）

以下均为**官方仓库 open 状态、无异常抛出、返回错误答案**的已知问题：

| Issue | 现象 | 对本项目的风险 |
|---|---|---|
| `#8314` | 状态通道**引用透传** —— 普通节点**原地修改 state 会污染调用方输入** | 章节状态（伤势/装备）被静默污染 |
| `#8115` | 并行写竞态**静默丢 checkpoint**（30/30 复现） | 断点恢复丢失 |
| `#8826` | `datetime` **静默丢时区** | 时间戳不可靠 |

**缓解**：
- 节点内**不得原地修改** state 对象（必须返回新对象或使用 reducer）
- 并行分支**不得写同一状态键**（用 `Send` + reducer 明确合并语义）
- 时间统一存 **UTC ISO8601 字符串**（不用 `datetime` 对象过 checkpoint）
- 这三条写成**单元测试**（构造原地修改/并行写/时区场景，断言被检出）

### R-03d · 结构化输出接口选择（中）

| 项 | 内容 |
|---|---|
| 优先级（实测） | **`json_schema`（原生）> `function_calling`（工具调用）> `json_mode`** |
| 关键证据 | **DeepSeek 官方承认 JSON Output "may occasionally return empty content"** |
| 与旧项目现象的关联 | 这**可能正是旧项目空输出率 22.2% 的成因之一** —— 而旧项目的 `_salvage_truncated` / `_note_micro_output_discard` 正是在对抗这类缺陷 |
| 缓解 | ① 优先用 `json_schema`（provider 支持时）；② 退化为 `function_calling`；③ **避免 `json_mode` 用于中文长文本**；④ 保留 JSON 修复能力（旧项目的控制字符转义修复在生产**高频生效**，实测一次修了 110 个未转义控制字符） |

### R-03e · 多 Agent 拓扑选型（★ 已形成结论，影响架构）

| 项 | 内容 |
|---|---|
| 结论 | **用确定性 custom workflow，不要 supervisor 自由路由** |
| 证据 1 | 官方成本表：subagents 模式 **4 次模型调用**，router 只需 **3 次** |
| 证据 2 | **Anthropic 明确把「所有 agent 共享同一上下文」列为多智能体不适配场景** —— 而这正是小说圣经的形态 |
| 证据 3 | `langgraph-supervisor` **已停止维护** |
| 与本计划的一致性 | ✅ `01-总体架构` 的分层子图（主图=阶段、子图=环节）正是**确定性图**，与该结论一致 |

### R-03f · 长任务存储与 Store 的适用性（中）

| 项 | 内容 |
|---|---|

### R-03g · DeepSeek 模型名已过期（★ 新发现，高）

| 项 | 内容 |
|---|---|
| 风险 | 旧项目使用的 `deepseek-chat` / `deepseek-reasoner` **已于 2026-07-24 停服** |
| 影响 | 任何沿用旧模型名的配置会直接失败 |

### R-03h · 缓存倍数与失效语义（中，修正一个常见误解）

| 项 | 内容 |
|---|---|
| 实测倍数 | DeepSeek 缓存命中/miss = **50×**（flash）/ **30×**（v4-pro） |
| 修正 | 不是常被引用的「10×」（那是 2024 年官方措辞，R1 时代实际仅 3.9×） |
| 与旧项目 Credits 权重的一致性 | ✅ 旧项目 MiMo 权重 `hit=2 / miss=100` = **50×**，与实测吻合 → 本计划的成本归因结论（hit 占 0.35%、output 占 77.5%）**成立** |
| ⚠️ 前缀失效是**全有或全无** | `SummarizationMiddleware` / `trim_messages` 会**永久改写 messages** → 缓存全废；`@dynamic_prompt` 是缓存杀手。<br>官方 `wrap_model_call` 的 *"Append at end"* 注入位置**恰好是缓存友好的** → 与对策⑦的「稳定前缀 + 易变尾部」一致 |
| 官方低谷价 | = 峰值价的一半（旧项目 `offpeak.py` 关注此事，但杠杆比想象小） |

### R-03i · Token 按节点归因的正确做法（中，影响观测设计）

| 项 | 内容 |
|---|---|
| ✅ 官方简单路径 | `stream_mode=["updates"]` 的 **dict key 就是节点名**，value 带完整 `usage_metadata` |
| ⚠️ 陷阱 | `UsageMetadataCallbackHandler`（core 0.3.49+）**只按 `model_name` 归因、不按节点**（已逐行读源码），且有 **4 条静默失败模式** |
| 影响 | 对策⑦的 `llm_calls.node_name` 必须靠 `stream_mode` 或自建 callback 获得，**不能依赖现成 handler** |

### R-04 · 阈值标定主观（高）

| 项 | 内容 |
|---|---|
| 风险 | 打分卡阈值定得松→无效，定得紧→误拦 |
| 实测证据 | 旧项目 `dialogue_floor = 0.12` 明显过松（Editor 反复批评"对话占比极低"而 12% 就合格）；而 `outline_lint` 一旦阻断会让既有书**立刻停止写作**（实测 412 项 error） |
| 缓解 | ① 用旧项目 **8 本书 × 全部章节**测量分布；② 人工盲读抽样校准；③ **记录标定依据**（哪本书、多少章、什么结论）；④ 阈值放 `config/thresholds.toml` 可调；⑤ 新阈值先 shadow 观察假阳性率（但要遵守 R-05 的退出期限） |

### R-05 · shadow 模式长期不退出（高，旧项目已实证）

| 项 | 内容 |
|---|---|
| 风险 | 校验器建好但一直 shadow，等于没有 |
| 实测证据 | 旧项目 `ultra_structure_config.json` = `enabled: false, shadow: true`（**指标设计正确却从不阻断**），导致 400 章挤一卷、411 项 lint error 全部放行；`prose_style` 同样 shadow，导致"AI 味"只观测不拦截 |
| 缓解 | `shadow_registry`：**任何 shadow 校验器必须在 N 次运行内（默认 20）产出明确决策**并记录；超期未决策则在启动日志与报告中**显著告警** |

### R-10 · 模型行为跨厂商不一致（中）

### R-11 · 人工确认点成为瓶颈（低）

### R-12 · uv / SQLite 的规模上限（低）

| 项 | 内容 |
|---|---|
| 风险 | 1,500 章 × 每章正文（~6,000 字）= 约 900 万字，SQLite + 文件存储是否够 |
| 实测证据 | 旧项目 `rag.json` 单文件 **27.75 MB**（book 8），每章重写一次 → 286 章约 **2.9 GB 磁盘写**。这是**存储设计问题**，不是 SQLite 限制 |
| 缓解 | ① 正文按章独立文件（不整份重写）；② RAG 索引**增量**维护（旧项目已实测 `docstore.rag_append` 约 20ms/章且线性，但整文件 JSON 是浪费）；③ 监控 DB 体积 |

## 5. 应对「已证伪的优化」（避免重走弯路）

旧项目已经用实测**证伪**或**否决**了若干看似合理的优化。新系统**不应重复投入**：

| 优化想法 | 旧项目结论 | 证据 |
|---|---|---|
| 砍 reasoning 长度以省成本 | **已证伪**，收益≈0 | `test_reasoning_caps.py` 用 **74 条真实 attempt** 验证配置上限从未撞到（editor 峰值 3853 vs 上限 5000） |
| 图谱 O(n²) 优化 | **已证伪** | 实测 1500 事件 `build_graph` 仅 **0.039s**；极端构造 5310 节点/17460 边仅 **0.102s** |
| `novelty` O(n²) 优化 | **已评估并决定不做** | 实测确认 O(n²)（100→1500 章：0.20s→28.85s），但**不在生成热路径**（仅按需接口触发） |
| 为「无推进重复（注水）」建确定性检测 | **四次验证全部失败** | 段级 Dice 最高 0.519（`>=0.60` 章数 0/47）；句级重复 0/47；内容单元法在已知坏样本上报 **0.0%**；低阈值探针命中 0。**根本原因**：同一拍会换一批词，且注水段落一直在引入新道具与编号 |
| 用离线 benchmark 成本排名做决策 | **不可用** | 离线显示 `editor 59.3%` 第一，生产实测 `architect 42.1%` 第一（离线严重欠采样 architect：生产 401 条 vs 离线 26 条） |
| 大输出一次性重写结构 JSON | **禁止** | book23/25 两次 ROLLED_BACK 的根因；必须走增量补缺 |
