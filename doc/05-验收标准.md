### 1.2.1 ★ learn 模式的指标差异（**不得套用 §1.2 的文风指标**）

> **状态**：2026-09-24 并入（源自 `doc/learn-验收标准-草稿.md`，
> 用户已确认决策①②③）。B1 核验节点**已实现**（commit `1c185e2`）。

learn 是**知识小说**：它要"把知识讲对、讲得不枯燥"，
而不是"把故事写得好看"。**直接套用 §1.2 的文风指标会判错**：

| §1.2 的 story 指标 | 套到 learn 上的问题 |
|---|---|
| 对话占比 **>25%**（严格） | ★ 教学章"**不要对话**"才是**正确**写法 —— 该指标会**硬触发** |
| 套话命中 `CLICHES:86` | `综上所述` 是**教学标准连接词**，却被当套话 |
| `golden_three`（黄金三章） | 教学章的"三章"承担的是**知识铺陈**，不是钩子密度 |

**实测证据**（2026-09-18）：用 story 打分卡评一篇**标准说明文**：

```
score = 0.51 / passed = False
triggers = [golden_three, dialogue_low, sentence_uniform, too_short, low_score]
```

其中 `dialogue_low` 是**硬触发**——而教学章本就该少对话。
⇒ **不是调参问题，是维度集合错配**（`style_critic.md` 的 6 项审查重点、
`reviewer.py` 的 `CATEGORY_RULES` 同样全是小说判据，需一并重写）。

**learn 专属指标**见 §1.2.2；learn 的功能/对比/准确性验收见 §1.4。

### 1.4 ★ 知识准确性验收（learn 专属，方案 B1）

> **状态**：2026-09-24 实现并并入（commit `1c185e2`）。
> 用户决策③：准确性采用 **LLM 交叉核验**（方案 B）。

#### 核验什么

对每条知识点判断**是否被研究资料支撑**，输出三态：

| 判定 | 含义 | 处置 |
|---|---|---|
| `supported` | 资料里有**直接依据** | 计入通过 |
| `inferred` | 资料未直说，但可**合理推得** | 计入通过（标记） |
| `unsupported` | 资料里**找不到任何依据** | ★ 计入失败（疑似幻觉） |

**关键区分**：`inferred` **不等于** `unsupported`。
教学需要"把资料讲透"，合理推演是**必要的**（由「点茶用茶筅」
推出「茶筅是核心器具」）。一刀切要求"逐字有据"会让地图退化成资料摘抄。

#### 谁来核验（★ 防"自己批自己"）

**核心要求：核验侧必须与生成侧可区分**，否则等于自证。

| 方案 | 核验侧 | 防自证强度 | 可用？ |
|---|---|---|---|
| **B1（已实现）** | `mimo-v2.6-pro`（premium）+ 独立 prompt | ★★ 换模型档位，不同权重 | ✅ |
| B2 | 同模型（flash）+ 独立 prompt | ★ 同权重仍有共谋风险 | ✅ |
| B3 | 异厂商（`deepseek-v4-pro`） | ★★★ 最强 | ❌ **缺 key** |

★ 实现上**由 `tier` 驱动，不写模型名**（决策 D-09）：
配上 `DEEPSEEK_API_KEY` 后调整候选顺序即可升级到 B3，**无需改代码**。

#### 判据与门槛

```
准确率 = (supported + inferred) / 总知识点数
```

| 判定 | 条件 |
|---|---|
| 严格 | 准确率 **≥85%** |
| 硬门禁 | `unsupported` **不得连续 3 条**（集中幻觉比分散更危险） |
| 留痕 | 每条 `unsupported` 必须记录**模型给的驳回理由**，供人工复核 |

#### 执行命令

```bash
uv run storyforge learn-map gen --book-id <书> --topic <主题> --scale fast
# 输出含：🔍 知识准确性核验（独立模型档位）：准确率 X%（N 有据 / M 可推 / K 无据）
#        准确性    ：准确率 X%（N 条已核验）

# 核验器**自身**的区分力验证（★ 必须做，见下）
uv run python scripts/probe_verify_discrimination.py
# 断言：故意编造的知识点被判 unsupported
```

#### ★ 三道防线（防"假绿"）

1. **空结果准确率 = 0.0**，不是 1.0 —— 没有判定 ≠ 全部通过
2. **未知判定单独计数**，不塞成 `supported` —— 把"判不了"伪装成
   "通过"就是给假绿（本项目反复吃过的形态）
3. **条数不符要报** —— 模型漏判等于"部分未核验"

#### ★ 为什么必须验证"核验器自己"

真实链路首跑得到 **准确率 100%（0 条无据）**。这有**两种**可能：

- 好事：地图确实都有依据
- 坏事：**核验器是恒真断言** —— 永远说"通过"

本项目已反复吃亏于"抓不到问题的检查等于没有"（规则 3 四类漏检、
规则 22 完全失效、`validate_map` 只查"有没有"不查"对不对"），
故对核验器**自身**也要证伪一次。实测（`probe_verify_discrimination.py`）：

```
喂真实资料 + 1 条故意编造（"南宋临安茶坊已采用磁悬浮茶筅配合量子纠缠控温"）
→ ★ [unsupported] 理由：所有资料均未提到磁悬浮、量子纠缠…属明显编造
→ ✓ 核验器有区分力，不是恒真断言
```

#### 诚实标注（限制）

- 草稿原写"核验温度 0"，但 **client 全链路不支持 `temperature`**
  （实测 `grep temperature src/` 零命中）→ 改用两道**结构性**手段替代：
  独立 prompt + 不同模型档位
- **B1 不是强隔离** —— 同代模型可能共享训练数据与偏见。
  实测只证明"在**明显案例**上有区分力"，**不代表能抓住微妙幻觉**
- 故判据保留**人工抽检**作为最终防线，不能只信自动核验

```
learn 卡 → triggers=[intra_redundancy]                  ← 真实冗余，非误杀

```

| 阈值组 | 状态 |
|---|---|

## 3. 质量回归测试（golden fixtures）

**目的**：防止"改一处、坏一处"。

```
tests/golden/
├── fixtures/
│   ├── chapter_01.json          # 固定输入（圣经+细纲+状态）
│   ├── chapter_01.expected.json # 期望的打分卡输出（零 LLM 部分）
│   └── ...
└── test_scorecard_golden.py
```

**规则**：
1. **零 LLM 部分必须有 golden 测试**（打分卡、lint、闸门、调度器）—— 这些是确定性的，可精确比对
2. **LLM 部分不做逐字节比对**（不可能稳定），改为**断言性质**：
   - `volume_plans` 满足 schema
   - 审校输出满足结构约束
   - 重试上限被遵守
3. golden 文件更新必须**显式说明原因**（防止悄悄放宽断言）

### 3.1 ★ 新增检查器的强制要求（2026-09-24）

> 从 learn 溯源/核验两项的实测归纳出的**通用纪律**。
> 适用于**任何**新增的校验、契约、诊断脚本。

| # | 要求 | 为什么 |
|---|---|---|
| 1 | 新增带 JSON 输出的节点，**必须登记 `STRUCTURED_NODES`** | ★ 同类漏洞**已栽三次**：缺陷 11 的 3 个抽取节点、`style_critic`、以及"设计完 prompt 却没登记"。漏登记 ⇒ prompt 长期无骨架而**契约全绿** |
| 2 | **必须写变异测试**证明"删掉它会红" | 一个"抓不到问题"的检查**等于没有**。已栽：规则 3 四类漏检、**规则 22 完全失效**（写完 pytest 全绿但抓不到目标缺陷） |
| 3 | **必须证明它能抓到已知的坏样本** | ★ 本轮新增：核验器首跑得"准确率 100%"，需排除"它是恒真断言"。做法是喂一条**故意编造**的样本，看它抓不抓（`scripts/probe_verify_discrimination.py`） |
| 4 | 校验器不得只查"**有没有**"，要查"**对不对**" | `validate_map` 只查"URL 非空" ⇒ "11 条知识点全挂同一组 URL"的**假溯源**全绿通过 |
| 5 | 误报比漏报更危险 | 误报会诱使人**删规则**而非修代码（规则 12 第一次运行即误报过，故改用 AST 而非子串匹配） |

**★ 第 3 条的由来（值得单独记）**：核验节点真实跑出 **100% 准确率**。
这有**两种**可能 —— 好事（地图确实好）或坏事（**核验器恒真**）。
不排除第二种，就无法把"100%"当成结论。故专门构造了一条
明显编造的知识点（"南宋临安茶坊已采用磁悬浮茶筅配合量子纠缠控温"）
喂进去 → 被判 `unsupported` 且理由精确 ⇒ 区分力得到证明。

## 4. 反模式检查（AST 级约束）

这些是用**机器检查**防止旧项目问题复发的硬约束：

| # | 检查 | 防的是什么（旧项目/ LangGraph 实证） |
|---|---|---|
| 1 | `domain/` 不得 import `langgraph` / `langchain` | 框架侵入业务逻辑 |
| 2 | `scorecard/` 不得 import `infra.llm` | 打分卡必须零 LLM（可复现） |
| 3 | `domain/` 与 `graph/nodes/` 不得出现 `book_kind` / `is_story` 判断 | 旧项目门面外仍有 30+ 处直读模式 |
| 4 | 任何模块不得出现 `model == "..."` 硬编码 | 旧项目"思考预算"策略不具跨模型鲁棒性（mimo 0% vs qwen 91.4% 空输出）；且 DeepSeek 模型名已过期（`deepseek-chat` 2026-07-24 停服） |
| 5 | `graph/state.py` 的 State 字段不得含 `str` 型大文本字段 | 旧项目把 outline/content 塞进 JSON 列；LangGraph checkpoint 官方承认 200 轮 **5.3 GB** |
| 6 | 每张表必须有 `FOREIGN KEY`（除根表），且连接时必须 `PRAGMA foreign_keys=ON` | 旧项目 0 FK，靠人工清单清理，漏过 6 张表；SQLite 默认**不强制** FK |
| 7 | 章号字段类型必须为 `int` 且单调递增 | 旧项目 `vol*10000+idx` 双表示导致 P0 事故 |
| 8 | 枚举必须有唯一来源（不得在多处重复定义） | 旧项目 severity 代码 5 档 / prompt 3 档 → **最重的伤不催、轻伤催得最凶** |
| 9 | 不得有以业务实例命名的模块（如 `book23_*.py`） | 旧项目 `book23_ultra_repair.py` / `book25_ultra_repair.py` |
| 10 | 单函数不得超过 200 行；单文件不得超过 800 行 | 旧项目 `_commit_chapter` 1,239 行、`pipeline.py` 8,607 行 |
| 11 | 测试文件不得在模块级修改 `os.environ` | 旧项目 121/123 个测试文件这么做 → 单进程 pytest 假失败 |
| 12 | 配置只从 `Settings` 读取，不得 `os.environ` 直读散落 | 旧项目 `.env` 写模型被 JSON **静默覆盖** |
| 13 | **节点不得原地修改 state 对象** | ⚠️ `langgraph#8314` 状态通道**引用透传** → 原地改会**污染调用方输入**（静默数据损坏） |
| 14 | **并行分支不得写同一状态键** | ⚠️ `langgraph#8115` 并行写竞态**静默丢 checkpoint**（30/30 复现） |
| 15 | 时间字段必须存 **UTC ISO8601 字符串**，不得用 `datetime` 对象过 checkpoint | ⚠️ `langgraph#8826` datetime **静默丢时区** |
| 16 | **每个 LLM 节点必须有幂等键** `(book_id, chapter_no, node_name, attempt_no)` | ⚠️ `langgraph#7417`（53 评论 open）：>180s 调用被**静默重放** → 2~3× 冗余成本。旧项目 `editor` 平均 **117s**，章节生成极易超阈值 |
| 17 | **每个写出的信号必须有读取点**（`must_*` / `needs_*` / `*_flags`） | ⚠️ 旧项目 `must_review` **25 处写入 0 处读取** → 整条文风控制链失效 |
| 18 | 每个 prompt 中的数量/结构要求必须有校验器与测试 | 旧项目 `entry_state` 13%、`milestone_ids` 0%、`conflict_curve` 从不校验 |
| 19 | 正文/细纲 JSON 不得进入图 State | 防 checkpoint 膨胀（官方 5.3 GB 案例） |
| 20 | 无 `LANGSMITH_*` 环境变量时系统必须完全可用 | 防 SaaS 锁定；用户要求"评测后续再加" |

**实现**：`tests/contract/test_architecture_invariants.py`，用 `ast` 模块静态扫描。
**CI 门禁**：任一条失败即阻断合并。
