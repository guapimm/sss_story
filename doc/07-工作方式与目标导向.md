# 工作方式与目标导向（项目记忆）

> **性质**：本文记录项目负责人明确要求的工作方式与优先级。
> **效力**：与 `00-决策记录.md` 同级 —— 后续任何人（含 AI 助手）接手时**先读本文**。
> **记录日期**：2026-09-13

---

## 1. 协作方式（硬要求）

| # | 要求 | 具体做法 |
|---|---|---|
| 1 | **按计划一步一步进行** | 一次只推一项；不要在一个回合里并行铺开多个不相关任务 |
| 2 | **梳理计划前多次思考、确认可行且无 bug** | 方案落地前先自查：会不会引入循环依赖？会不会与已有机制冲突？边界情况是否覆盖？ |
| 3 | **需要确认的细节主动发起提问** | 不要自行替负责人拍板有实质影响的选择（枚举命名、阈值、抽象层次、优先级）。用提问工具直接问 |
| 4 | **完成一项后及时更新任务列表** | `todo_write` 打勾；不要让清单与实际进度脱节 |
| 5 | **执行完一个大阶段后做完备测试** | 不是"跑一下看看"，而是全量测试 + `doctor` + 真实链路验证 |

### 1.1 Codex 模型与额度约束（2026-09-23 新增，硬要求）

以下约束针对**协作时使用的 Codex 模型**，不改变小说生成系统在
`config/providers.toml` 中的运行时模型路由。

1. **详细思考、梳理代码方案和实施计划使用 GPT-6 Sol**（`gpt-6-sol`）。
2. **写代码及其他重复、消耗量大的执行工作使用 GPT-6 Luna**（`gpt-6-luna`）。任务分工按实际活动划分，执行前确认所用模型；不可静默换成其他模型，也不可把计划阶段的模型选择误当作代码执行阶段的选择。
3. **每次任务开工前查看 Codex 的 5 小时窗口和周额度**：记录当时的剩余量与重置时间，估算计划、执行、验证及收尾所需额度，并留出完成当前阶段的余量。额度是实时状态，每次重新查询，不把某次查询的百分比当成长期预算。
4. **按可独立完成和验收的阶段安排工作**。如果当前额度不足以完成一个阶段的实现与验证，先缩小到能交付的阶段，或在开始高消耗步骤前等待额度恢复；不要启动一个大概率执行到一半就因额度耗尽而停止的阶段。阶段结束要留下可复核的结果与下一步入口。
5. 若当前会话无法切换到指定模型，明确说明实际可用的模型与限制；不要声称已经按指定模型执行，也不要未经用户同意自行替换模型。

### 为什么要求「多次思考确认可行」

本项目已经吃过**三种同类亏**（都是"看起来能跑，实际一跑就崩"）：

1. `volume_planner` 读 `settings.structure_gate.shadow` —— 该字段**不存在**，
   只在真实运行时才炸 `AttributeError`。
2. `Orchestrator.queues` 只建 3 个队列 → `BIBLE` 阶段 `enqueue` 直接 `KeyError`。
   四个不变量用哑 worker 全绿，却没有一条测试真的走过 BIBLE。
3. `StateGraph(dict)` 丢弃未知键 → 所有节点 `KeyError`。图"编译通过"，
   但一次都没真跑过。

**共同点**：测试只验了"能编译/能构造"，没有真跑。
因此本项目的验收标准包含一条：**新机制必须有一条端到端真跑的测试**，
而不是只验证它能被构造出来。

## 2. 目标导向（判定一切取舍的最终标准）

### 2.1 代码质量

| 目标 | 具体含义 | 当前的落地手段 |
|---|---|---|
| **低耦合** | 分层单向依赖；领域层不依赖框架；节点之间不互相调用 | 20+ 条 AST 契约测试（`tests/contract/`） |
| **方便维护** | 单一来源；配置驱动；文件 ≤800 行、函数 ≤200 行 | 枚举只在 `domain/enums.py`；模型与价格在 `providers.toml`；契约规则 10 |

**判定原则**：任何"为了方便"而引入的跨层调用、重复定义、硬编码，
都必须先说明为什么契约测试应该为它破例 —— 默认答案是"不该破例"。

#### 2.1.1 ★★ 拆分与重构的判据：**看耦合，不看行数**（2026-09-24 负责人明确要求）

| 项 | 内容 |
|---|---|
| **要求** | **不要为了"接近行数上限"而强行拆文件。** 只要**功能低耦合、后续改动方便**即可 |
| **判据** | 拆分的理由是**耦合**：一个文件里装着**互不相关**的职责、改动 A 总要顺带改 B、测试必须构造一堆无关依赖才能测一处 |
| **不构成理由** | ❌「已 734 行，快到 800 了」 ❌「拆了看起来更整齐」 ❌「别的文件都比它小」 |
| **行数上限的真实定位** | 规则 10 的 800 行是**兜底红线**（防旧项目 `pipeline.py` 8,607 行那种失控），**不是拆分触发器**。它只回答"**已经**太大了吗"，不回答"该拆了吗" |

**为什么这条要单独立规矩**（本项目刚吃过一次亏）：

> 2026-09-24，我（AI 助手）在完成 learn 打分卡后主动提议
> 「`cli.py` 734 行、`enums.py` 776 行接近上限，下次加代码前先拆」。
> 负责人当场纠正：**没必要硬拆**，低耦合就行。

我当时的推理错在**把代理指标当成了目标**：行数是"耦合度高"的**可能信号**，
不是**充要条件**。一个 776 行的文件若只做一件事（`enums.py` 就是
"所有枚举的单一来源"，这正是它的职责），那它是**内聚**的，
拆开反而**增加**耦合（枚举散落多地 = 破坏"单一来源"，见 §3 反模式）。

**推论（对既有做法的澄清，不是推翻）**：

| 历史事件 | 是"为行数拆"吗 | 真正的拆分理由 |
|---|---|---|
| `cli.py` → 拆出 `doctor.py` | ❌ 不是 | `run_doctor` 与 CLI 参数解析是**两个职责**，且 doctor 可独立测试 |
| `cli.py` → 拆出 `commands/learn.py` | ❌ 不是 | learn 命令群与 story 命令群**几乎不共享状态**，learn 线还要独立演进 |
| `commands/learning.py` → 拆出 `learning_gen.py` | ❌ 不是 | 生成（调 LLM）与读写/CLI 操作（纯 I/O）**依赖方向不同**，混在一起让"读写"被迫引入 LLM 依赖 |

★ 三次拆分都**恰好**在接近 800 行时发生，所以看起来像"为行数而拆"。
但当时的理由都是**职责分离**。**记录于此以免后人误学成"到 800 就拆"。**

**操作要求**：

1. 新代码放哪里 —— 按**职责归属**决定，不按"哪个文件还有空位"决定
2. 真要拆时，先说清**拆完降低了哪一处耦合**（说不清就别拆）
3. 内聚的大文件**允许存在**；只要它 ≤800 行且只做一件事


### 2.2 生成的小说质量

这是**项目的根本目的**，前面所有基建都服务于它。四个维度：

| 维度 | 含义 | 旧项目实测的反面教材 |
|---|---|---|
| **去除 AI 味，更像真人写手** | 少套话、少比喻、不直接命名情绪、句长有变化、对话占比合理 | 旧项目 `ai_style` 以 228 条居 issue 首位；88.1% 章被点名文风问题 |
| **记忆系统完备** | 人物/势力/关系/装备/伤势/伏笔都要有账本，且**每章都被注入** | 旧项目记忆密度从第 50 章 4.8% 衰减到第 1500 章 **0.16%** |
| **长文不出 bug** | 跨章一致性：章号口径、状态衔接、实体不凭空出现/消失 | 旧项目 `since_ch` 卷内号/全书号混用 →「已持续 10011 章」 |
| **逻辑完美** | 事件有动机、转折有铺垫、角色不知道不该知道的事 | 旧项目 400 章困在一栋楼里（门/电梯/走廊） |

**判定原则**：当一个改动会让上述任一项变差时，**即使它省 token 也不能做**。
用户已明确表态：**质量优先，不要为了省 token 牺牲质量**。

### 2.3 三个已被验证的质量杠杆（实测证据）

按性价比排序，这三条比"调 prompt 措辞"重要得多：

1. **结构先行** —— 卷级升级台阶 + 骨架必须落实扩张。
   旧项目失败不在文笔，在**大纲层从未规划过扩张**（后半本新增地点 0~1 个）。
2. **闸门必须真阻断** —— 旧项目 `ultra_structure_config` 指标设计正确，
   但 `enabled: false, shadow: true`，于是 400 章全挤第 1 卷。
   **设计对了却关着的校验器，等于没有。**
3. **审校结论必须被消费** —— 旧项目 `must_review` 25 处写入、**0 处读取**，
   Editor 说的问题从不落地。本项目的对策是"修订稿必须过闸门（分数不升则拒绝）"。

## 3. 反模式清单（本项目明令禁止）

| 反模式 | 为什么禁止 |
|---|---|
| **静默降级** | 读不到就返回空串/dict/0 —— 旧项目 `read_chapter` 静默返回空串导致正文丢失不报错 |
| **缺省即通过** | 校验器只挡"错误值"、不挡"缺失值" —— 旧项目 `entry_state` 填充率仅 13% |
| **写出的信号无人读** | 契约规则 11 强制；旧项目 `must_review` 是标本 |
| **只报告不阻断（shadow 模式）** | 让"已实现"与"在生效"变成两件事，且报表上看不出区别 |
| **一次抽太多** | 旧项目单 prompt 抽 11 类 → `entity_classify` 空输出 **100%** |
| **失败即放弃** | 解析失败与闸门失败应走**同一条修复路径**；旧项目两次 ROLLED_BACK 就是一次失败即放弃 |
| **误报诱人删注释** | 过宽的检查会把解释性注释一起判违规，最终导致教训失传 |
| **字段名靠散文描述** | 模型会自造同义名（实测 `volume_title`/`core_focus`），每次不匹配都让整轮失败 → 必须给 JSON 骨架 |
| **为行数而拆文件** | 行数是"耦合度高"的**可能信号**，不是拆分理由。内聚的大文件（如 `enums.py` = 枚举单一来源）拆开只会**增加**耦合。拆分必须能说清"降低了哪一处耦合"（详见 §2.1.1） |

## 4. 验收纪律

每个大阶段结束时必须逐条执行（见 `05-验收标准.md`）：

```powershell
uv run pytest                      # 全量测试必须绿
uv run storyforge doctor           # 自检必须 PASS
uv run storyforge baseline --dir "E:\AI_project\story_llm\backend\storage\story\books\23\chapters"
                                   # 口径一致性必须全 OK（地基验收）
```

**并且**：涉及真实 LLM 的改动，必须**真跑一次**（`storyforge plan` / `write`），
不能只靠脚本化 transport 的测试。理由见 §1 的三种亏。
